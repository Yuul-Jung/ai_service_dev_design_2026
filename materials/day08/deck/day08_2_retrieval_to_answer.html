순위 결합Reciprocal Rank Fusion (RRF)

점수의 척도가 다른 두 검색 결과를 ‘몇 번째인가’라는 같은 단위로 합칩니다. 점수 = Σ 1 ÷ (k + 순위)이며 상수 k는 도구마다 다릅니다(LangChain 60, Supabase 50).

리랭킹Reranking (cross-encoder)

질문과 후보를 함께 읽어 점수를 다시 매깁니다. 후보 수만큼 처리가 늘고, 이번 질문에서는 20쪽이 밀려났습니다(p.52–54).

서로 다른 점수는 순위로 합치고, 검색된 원문은 지시가 아닌 자료이며, 출처 번호가 붙었다고 근거가 맞는 것은 아닙니다.

01키워드 검색과 의미 검색 · 순위 결합(RRF)p.48–51

자료 p.48–49

정확한 표현으로 찾는 키워드 검색: 이름·용어·코드를 그대로 찾는 데에는 문서에 그 표현이 있는지가 중요하다. 앞 질문에서 고른 표현(데이터 · 저장 · 연결)이 원문에 있는지 먼저 찾는다. 의미가 비슷한지 비교하는 방식과 결과가 다를 수 있다. 같은 질문에서 서로 다른 후보가 나왔다. 표현을 맞춰 찾기: 19쪽 · 22쪽 · 20쪽 · 21쪽. 의미를 비교해 찾기: 22쪽 · 19쪽 · 17쪽 · 20쪽.

자료 p.50–51 · 순위 결합

의미 검색: 1위 T22, 2위 T19, 3위 T17, 4위 T20. 키워드 검색: 1위 T19, 2위 T22, 3위 T20, 4위 T21. 결합 결과: T19·T22 동점, 3위 T20, 4위 T17. “T20: 의미 4위 + 키워드 3위 → 각 순위의 기여를 합산.” 같은 후보를 연결해 합치므로 한쪽에서 낮았던 자료도 올라올 수 있다. 결합 전후 상위 3개: 의미 검색(22·19·17쪽) → 결합 뒤(19·22·20쪽).

검증 · 순위 결합의 결과를 직접 계산 (RRF) p.50–51 일치 추가 계산

순위 결합 점수 = Σ 1 ÷ (상수 k + 그 목록에서의 순위) (목록에 없으면 0) k = 60: T19 0.03252 = T22 0.03252 > T20 0.03150 > T17 0.01587 > T21 0.01562 k = 50: T19 0.03884 = T22 0.03884 > T20 0.03739 > T17 0.01887 > T21 0.01852

슬라이드의 결합 결과(T19·T22 동점, 3위 T20, 4위 T17)가 k = 60과 k = 50 모두에서 재현됩니다. T19와 T22는 두 목록에서 순위를 서로 맞바꿔 가지므로(1+2 대 2+1) 어떤 k에서도 같은 점수입니다. T20은 의미 4위와 키워드 3위를 합산해 T17(의미 3위, 슬라이드가 보여 준 키워드 상위 4개에는 없음)을 앞섭니다. 위 계산은 두 목록에 보이지 않는 자료의 점수를 0으로 둔 것이며, 실제 시스템에서는 더 낮은 순위에 있을 수 있습니다. “한쪽에서 낮았던 자료도 올라올 수 있다”가 숫자로 확인됩니다.

공식 문서의 상수: LangChain의 앙상블 검색기는 가중 RRF를 쓰고 상수 c = 60이 기본이며, Supabase의 하이브리드 검색 문서는 rrf_k int = 50과 1 ÷ (rrf_k + 순위) 식을 보여 줍니다. 두 문서가 쓰는 상수가 다르므로 결합 결과는 도구에 따라 달라질 수 있습니다(이 예에서는 달라지지 않았을 뿐입니다). 슬라이드는 어떤 상수를 썼는지 밝히지 않았으며, 위 두 값 모두에서 같은 결과가 나온다는 것만 확인했습니다.

보충 · 서로 다른 점수를 왜 순위로 합치는가

키워드 검색의 점수(단어 빈도 기반)와 의미 검색의 점수(코사인 유사도)는 척도가 달라 그대로 더할 수 없습니다. 순위는 두 척도 모두에서 ‘몇 번째인가’라는 같은 단위이므로 합칠 수 있습니다. 이것이 p.75의 “서로 다른 점수를 가진 검색 결과를 왜 순위로 결합할까?”의 답입니다. Supabase 문서도 RRF의 핵심을 “각 결과 목록에서 상위 항목에 더 큰 가중을 주는 것”이라고 설명합니다.

02리랭킹 · 찾은 후보를 질문과 함께 다시 읽어 점수화한다p.52–54

자료 p.52–54

리랭킹: 먼저 찾은 7개의 본문을 가져오고 → 질문과 각 본문을 함께 읽어 점수화하고 → 높은 점수부터 다시 정렬한다(이번 실제 계산: bge-reranker-v2-m3). 임베딩 검색은 질문과 원문을 각각 벡터로 만들어 비교하고, 교차 인코더 리랭킹은 질문 + 후보 A의 본문을 함께 처리해 후보 A의 점수를 낸다. “문서 벡터는 미리 계산할 수 있다. 리랭커는 질문과 후보를 함께 읽는다.” 재정렬 전 상위 3개(19·22·20쪽) → 재정렬 후 상위 3개(22·19·3쪽).

검증 · 리랭커의 종류와 임베딩 검색과의 차이 (공식 저장소) p.52–53 일치 모델 실행 미실행

bge-reranker의 공식 저장소(FlagEmbedding)는 이 모델들을 “교차 인코더(cross-encoder) 모델로, 임베딩 모델이 돌려준 상위 k개 문서를 다시 정렬하는 데 쓰기를 권한다”고 설명하고, 2024년 3월에 M3 기반의 다국어 리랭커가 공개되었다고 적습니다(bge-reranker-v2-m3가 이에 해당). sentence-transformers의 공식 저장소도 교차 인코더를 “리랭커(reranker)라고도 부르며 유사도 점수를 계산하는 모델”로 구분합니다. 즉 임베딩(바이 인코더: 문서와 질문을 각각 벡터로)과 리랭커(교차 인코더: 질문과 후보를 함께 읽음)의 구분이 슬라이드와 같습니다.

비용의 차이가 중요합니다. 문서 벡터는 미리 계산해 둘 수 있지만 리랭커는 질문이 들어온 뒤 후보 수만큼 질문과 본문을 함께 읽어야 합니다(7개면 7번). 그래서 리랭킹은 임베딩으로 추린 소수의 후보에만 적용합니다. 모델을 실제로 실행(가중치 접속 불가)하지 못해 슬라이드의 재정렬 순위(22·19·3쪽)는 대조하지 못했고, 구조·비용에 관한 설명만 확인했습니다.

주의 · 재정렬 결과도 원문으로 해석한다 (p.54)

재정렬 후 상위 3개에 3쪽(검토할 요소의 목록)이 들어오고 20쪽(종류·관계·형태)이 밀려났습니다. 리랭커가 모든 면에서 더 낫다는 보장은 없고, 이 질문에서는 구체적인 설명이 담긴 20쪽이 빠진 대신 목록 쪽이 올라왔습니다. 이후 평가(오후 2의 20쪽 추적)에서 이 문제를 다시 다룹니다.

기법하는 일쪽
메타데이터 필터질문과 비슷한가를 보기 전에 어떤 자료를 검색해도 되는지 정한다(문서 종류·작성일·버전·접근 권한). 선택할 값이 자료에 저장되어 있어야 하고, 권한 조건은 실제 검색·반환 처리에 적용한다p.55
부모–자식 분할작은 자식 조각으로 질문과 비교하고, 찾은 조각이 속한 큰 부모 범위(제목·주변 설명)를 함께 반환한다. 검색의 단위와 반환할 문맥을 따로 정한다p.56–57
맥락 보충 검색조각의 배경 설명을 붙여 검색한다. 주변 원문을 나중에 더 가져오는 방식과, 검색 표현을 미리 보충하는 방식이 있다p.58
질문 재작성사용자의 질문(“그 관계는 어떻게 정해?”)에서 대화 맥락으로 대상을 복원해 검색 문구를 구체화한다. 답변은 사용자의 원래 질문에 맞춰 만든다p.59
계획형 검색질문을 나눠(저장할 항목·관계 / 데이터 이동·처리) 각각 검색하고 겹치는 근거를 합쳐 필요한 본문·출처를 모은다. 검색 문구·찾은 자료·처리 기록을 읽어 원래 질문을 충분히 다뤘는지 본다p.60

검증 · 검색 범위와 반환 범위가 다르다는 것 (이 쪽들의 논리) 앞의 실험과 일치 제품 기능은 미확인

p.56–57의 부모–자식 분할은 앞 절의 청킹 실험이 보인 문제의 해법입니다. 작은 조각은 질문과 정확히 비교되지만 주변 설명을 잃기 쉽고(오전 04절: 겹침 0·4어절은 설명이 갈라짐), 큰 조각은 설명을 담지만 검색이 거칩니다. 그래서 찾는 단위(작게)와 돌려주는 단위(크게)를 나눕니다. p.58의 맥락 보충도 같은 문제를 다른 쪽에서 풉니다(조각에 배경 설명을 붙여 색인). p.60의 계획형 검색 중 Azure의 구현은 ‘LLM 계획 기능은 미리보기’라고 슬라이드가 밝혔으며 공식 문서에 접속할 수 없어 확인하지 못했습니다.

주의 · 권한 조건은 ‘찾기 전’과 ‘돌려주기 전’ 모두에 적용한다 (p.55)

슬라이드는 “권한 조건은 실제 검색·반환 처리에 적용한다”고 말합니다. 권한이 없는 자료가 후보로 검색된 뒤 답변 입력에 섞이면 모델이 그 내용을 답에 쓸 수 있으므로, 후보를 고르는 단계에서부터 접근 가능한 자료로 범위를 제한하는 것이 안전합니다(작성자 조언). 화면에서 숨기는 것만으로는 충분하지 않습니다.

04파일·위키 검색 도구와 검색 결과를 모델 입력에 넣기p.61–64

자료 p.61

파일과 위키에도 검색 도구를 붙일 수 있다. QMD는 내 컴퓨터의 Markdown 문서를 검색하는 도구다. 원자료·위키 폴더 → 검색할 폴더 등록 → 키워드·벡터 준비 → 질문 → 후보 찾기(query) → 키워드·의미 검색 → 순위 결합·재정렬 → 본문 읽기(get) → 필요하면 원자료도 읽기. 자료를 정리하는 방식과 읽을 자료를 고르는 방식은 함께 구성할 수 있다.

검증 · QMD의 구성 (공식 저장소) 일치

QMD의 공식 저장소는 이 도구를 “기기 안에서 도는 검색 엔진: Markdown 노트·회의록·문서를 색인하고 키워드나 자연어로 검색”한다고 설명하며, BM25 전문 검색 + 벡터 의미 검색 + LLM 재정렬을 결합하고(모두 로컬 실행) 원래 질문을 두 검색에 보낸 뒤 RRF로 결합하고 재정렬한다고 밝힙니다. 명령은 qmd query(하이브리드 + 재정렬)와 qmd get(문서 열기)이 있어 슬라이드의 query·get과 같습니다. 오전·오후 1에서 배운 키워드·의미·순위 결합·재정렬이 한 도구에 모두 들어 있는 예입니다.

자료 p.62–64 · 실제 모델 입력과 응답

의미 검색의 결과(T22 · 데이터 모델 설계 질문, T19 · 데이터 모델 설명, T17 · 아키텍처 설계 질문)가 답변 모델에 보낼 입력이 된다. 지시: 자료에 근거해 답하기 / 질문: 데이터와 관계를 정하려면? / 자료: T22·T19·T17의 본문. “관련성 점수가 답의 근거가 되는 것은 아니다. 선택한 원문을 읽게 한다.” 이번 질문에 실제로 전달한 내용: 답변에 준 지시(자료에 근거해 답한다 · 자료 번호를 주장에 연결한다 · 확인할 수 없는 내용은 구분한다). 실제 응답 중 일부: “데이터 간 관계가 실제 서비스의 동작과 일치하는지 확인하고, 데이터 흐름에 비효율이 있는지 점검해야 한다.”

p.63의 세 지시(근거에 따라 답하기, 번호를 주장에 연결하기, 확인할 수 없는 내용을 구분하기)는 7일차 p.121의 “작업 지시와 원문을 나눈다”와 같은 구성입니다. 한 가지를 더합니다. 검색된 원문은 자료이지 지시가 아닙니다. 7일차에서 본 대로 검색된 문서 안에 ‘앞의 지시를 무시하라’ 같은 문장이 있어도 모델이 따르지 않도록 지시와 자료를 나누고(완화책일 뿐 완전한 방어는 아님, 7일차 오후 둘째 05절의 OWASP 근거), 외부에서 가져온 문서일수록 이 위험이 큽니다. 슬라이드의 실제 모델 입력과 응답(p.62–64)은 슬라이드가 제시한 값이며, 이 환경에서는 모델을 실행하지 못해 재현하지 못했습니다.

05Dify·관리형 File Search·직접 구성(Supabase) · 맡길 범위의 차이p.65–74

자료 p.65–69 · Dify

Dify는 AI 서비스를 구성하는 도구다. 검색·생성을 노드로 놓고 입력과 출력을 연결한다(사용자 질문 → 지식 검색 → LLM → 답변 표시). 노드는 한 가지 처리를 맡는 구성 요소이며 선으로 이어져 있어도 입력 변수 연결을 읽어야 한다. 검색 노드는 Query Text ← 사용자 질문, 검색할 지식베이스를 선택하고 result(찾은 본문·출처 목록)를 내며, LLM 노드는 User 메시지 ← 사용자 질문, Context ← 검색 노드의 result를 쓴다. “실행 기록에서 검색 결과와 실제 모델 입력을 각각 펼쳐 연결을 확인한다.” Dify의 새 지식베이스는 자료 정리도 모델에 맡긴다(추론 모델이 절 구분·요약, 임베딩 모델이 검색할 표현을 만들고 깊이를 선택). 문서 보기(모델이 나눈 절·요약·조각)와 검색 시험(Retrieval Test)에서 확인한다.

검증 · Dify의 성격 일반 설명 일치 새 지식베이스·노드 화면은 미확인

Dify의 공식 README는 Dify를 “오픈소스 LLM 앱 개발 플랫폼”으로, AI 워크플로·RAG 파이프라인·에이전트·모델 관리·관측 기능을 직관적인 화면에서 결합한 것이라고 설명합니다. 슬라이드의 “검색·생성을 노드로 놓고 입력과 출력을 연결”한 구성과 같은 범주입니다. 다만 노드의 필드 이름(Query Text·Context·result), 새 지식베이스(베타)의 자동 정리와 Retrieval Test 화면은 공식 문서에 접속할 수 없어 확인하지 못했습니다(슬라이드는 이를 2026-11-10 확인, 베타로 밝힘). 슬라이드의 중요한 단서는 자료 정리를 모델에 맡기면 어떻게 정리되었는지 사람이 읽어 확인해야 한다는 것입니다(같이 읽어야 할 문장이 잘렸는가? 요약이 원문의 뜻과 맞는가?).

  • OpenAI: 응답 API의 file_search 도구는 vector_store_ids(사용할 벡터 저장소 목록)를 필수로 받고, 저장소를 만드는 자원(vector_stores)이 따로 있습니다. 같은 두 단계 구조입니다.

07핵심 정리

  • 키워드 검색은 표현의 일치, 의미 검색은 벡터의 가까움을 보며 후보가 서로 다릅니다. 두 순위는 RRF로 합치며 이 예에서는 T19·T22가 동점, T20이 3위로 올라옵니다(k=50·60 모두 같음). 상수는 도구마다 다릅니다.
  • 리랭커(교차 인코더)는 질문과 후보를 함께 읽어 점수를 냅니다. 후보 수만큼 처리가 늘고, 이번 질문에서는 20쪽이 밀려났으므로 결과를 원문으로 해석합니다.
  • 찾는 단위와 돌려주는 단위를 나누고(부모–자식), 권한 조건은 찾기 전부터 적용합니다.
  • 검색된 원문은 자료이지 지시가 아니며, 번호가 붙었다는 것과 근거가 맞다는 것은 다르고, 자료에 없으면 ‘확인할 수 없음’이 답입니다.
  • 관리형 검색은 저장소를 만들고 질문에 지정하는 두 단계(Google·OpenAI SDK)이며, 맡길수록 지원 형식과 출처 반환을 확인해야 합니다.
