02오전 · AI가 만든 계획과 구현을 이해하고 대조한다 [p.3–9]

자료 p.3–4 · 실제 제작 보고

브라우저에서 곡을 만들고 편집하는 앱의 요청(음악을 만드는 프로그램)에서 AI는 녹음하기(소리를 입력받기)·편집하기(소리 조각을 옮기기)·믹싱하기(소리를 함께 조절하기)를 계획했다. “기능 이름을 승인하기 전에, 사용자가 할 일과 어떻게 이어지는지 묻는다.” 같은 앱의 제작 → 평가 → 재작업 기록: 첫 평가(편집할 소리 조각을 옮길 수 없음), 두 번째 평가(녹음 버튼은 바뀌지만 소리는 입력되지 않음), 작성자의 최종 사용(AI에게 곡의 속도·악기·효과 조정을 요청). “겉모습의 완성이 아니라 실제로 할 수 있는 일이 다음 작업의 근거가 된다.”

‘실제 제작 보고’(Anthropic 앱 제작 보고, p.42에서 2026년 3월로 표시)의 원문은 접속할 수 없어 확인하지 못했습니다. 이 사례의 교훈은 7일차 p.65의 ‘실행됐다 → 기능이 동작했다 → 목적에 맞았다’와 같습니다. 화면에 녹음 버튼이 있어도 소리가 입력되지 않으면 사용자가 하려는 일은 못 하며, 그 ‘실제로 할 수 있는 일’이 다음 수정의 근거입니다.

자료 p.8–9

어느 AI의 작업을 보는가? 서비스를 만드는 AI(제작자의 요청을 받아 프로젝트 파일을 읽고 코드를 바꾸거나 실행)와 서비스 안에서 일하는 AI(사용자의 요청을 받아 서비스에 연결된 자료와 기능을 사용)를 구별하고, 다음 예에서는 왼쪽 AI가 구현 파일을 고치는 과정을 따라간다. 테스트는 기대한 동작과 실제 동작을 비교한다(구현 파일: 기능이 작동하는 코드, 테스트 파일: 확인할 조건과 기대 결과를 담아 실행 결과를 그 기준과 비교).

구현 파일과 테스트 파일은 역할이 다릅니다. 구현은 ‘어떻게 동작하는가’, 테스트는 ‘어떻게 동작해야 하는가’(기대 결과)를 담아서, 둘이 어긋나는 곳이 수정할 곳이 됩니다. 이 구분이 다음 절의 ‘테스트 실패에서 수정까지’를 이해하는 바탕입니다.

03오전 · 에이전트 SDK와 작업 루프 · 결과를 받아 다시 진행한다 [p.10–13]

자료 p.10–12

에이전트 SDK가 모델과 도구를 이어 준다(모델: 현재 입력에서 다음 행동을 요청 → 실행 프로그램: 요청한 도구를 실행하고 결과를 수집 → 다음 모델 입력: 도구에서 받은 결과를 포함). SDK는 이 연결을 앱에 넣을 수 있게 제공하는 개발 도구 묶음이다. 테스트 실패에서 수정·종료까지 이어지는 네 차례(Claude Agent SDK 공식 예, 구현을 수정해 테스트 통과까지 진행): ① 테스트 실행 → 3개 실패, ② 구현·테스트 파일 읽기 → 두 파일의 내용, ③ 구현 수정 후 테스트 재실행 → 3개 통과, ④ 최종 설명 응답 → 도구 호출 없이 종료. 한 차례에 여러 도구를 요청할 수 있다. 실행 결과는 다음 판단에 들어간다(3개 실패 반환 → 결과를 다음 입력에 포함 → 파일 읽기를 다음 행동으로 요청).

검증 · Claude Agent SDK의 존재와 차례·종료 사유 〔구조 일치〕 〔공식 예 문서는 미확인〕

Claude Agent SDK의 공식 저장소(Python)에는 에이전트 루프를 앱에 넣는 query 방식과 옵션 max_turns(“질의가 멈추기 전의 최대 대화 차례 수. 한 차례는 사용자 메시지 하나와 어시스턴트 응답 하나로 이루어진다”)가 있고, 질의 루프의 종료 사유(completed·max_turns 등)를 알려 주는 필드가 있습니다. 슬라이드의 ‘네 차례’는 도구 결과가 사용자 메시지 형태로 돌아오고 마지막 최종 응답도 하나의 응답이라는 점에서 이 정의와 일관됩니다. 다만 SDK가 정확히 어떻게 세는지는 이 환경에서 모델을 호출할 수 없어 실행으로 확인하지 못했고, 슬라이드의 ‘테스트 3개 실패 → 3개 통과’ 공식 예의 문서 원문도 확인하지 못했습니다.

자료 p.13

작업 루프는 결과를 받아 다시 진행하는 반복이다. 계획 → 실행 → 결과 읽기 → 다음 행동이 필요한 만큼 이어진다. 다음 행동은 수정뿐 아니라 추가 조사·질문일 수도 있다. 사람이 대화를 이어 갈 수도 있고, 프로그램이 모델·도구 호출을 반복할 수도 있다.

9일차 p.19–20의 ‘하네스가 요청 전달 → 도구 실행 → 결과 재입력을 잇는다’가 여러 번 반복되는 모습입니다. 반복을 사람이 이끄느냐(대화) 프로그램이 이끄느냐(루프)의 차이이며, 다음 행동이 항상 ‘수정’인 것은 아닙니다. 결과가 부족하면 조사하거나 사람에게 묻는 것이 맞을 수 있습니다.

자료 p.14–16 · Dify의 반복

항목별 반복(Iteration: 문서 A·B·C를 각각 처리해 결과 A·B·C)과 결과를 이어 쓰는 반복(Loop: 이전 초안을 읽고 수정해 갱신된 초안). 상태 변수에는 다음 반복에 쓸 값이 들어간다(상태: 현재 처리에 필요한 정보 / 변수: 그 값을 이름으로 참조하는 자리). Dify 공식 시 수정 예에서 verse(지금까지 작성한 시의 내용)와 num(현재 반복 차례)이 별도 값으로 이어지며, 값 갱신은 새 내용과 늘어난 횟수로 바꾼다(verse ← 새 내용, num ← 다음 차례). 다음 반복에서는 갱신한 값을 읽는다. “공식 예의 num > 3은 횟수를 확인한다. 내용의 품질을 판정하는 조건은 아니다.”

체크포인트는 실행 상태를 저장한 것이다(실행 중 상태: 현재 값·처리 위치 → 체크포인트: 저장한 상태 → 같은 흐름에서 불러오기). 스레드는 상태가 이어지는 작업 흐름이고 thread_id는 그 흐름의 식별자다. 프로그램 종료 뒤에도 필요하다면 상태가 남는 저장소를 사용해야 한다. 중단한 흐름은 필요한 입력을 받아 재개한다: interrupt(...)(진행에 필요한 외부 입력을 기다림), thread_id(어느 작업 흐름의 상태인지 찾음), Command({resume: ...})(기다리던 입력을 주고 실행을 이어 감). 같은 thread_id로 재개한다. 새 식별자는 별도 흐름을 가리킨다. LangGraph 공식 승인 예: ① 승인 질문에서 멈춤(“이 작업을 승인합니까?”) ② 같은 흐름에 답 전달(Command({resume: true}) → approved = true). 재개하면 노드를 처음부터 실행한다. 중단 전 외부 행동도 다시 일어날 수 있다.

슬라이드의 세 설명이 모두 재현됩니다. ① interrupt는 상태를 저장하고 멈춥니다(다음에 실행할 노드가 저장됨). ② 재개하면 해당 노드가 처음부터 다시 실행되어 interrupt 앞의 외부 행동이 1회에서 2회가 됩니다. ③ 같은 thread_id여야 같은 흐름을 이어 가고 새 식별자는 별도 흐름입니다. LangGraph 공식 저장소의 소스에서 interrupt·Command(resume=...)·체크포인트가 이 용도로 쓰이는 구조도 같았습니다. 그래서 interrupt 앞에는 되돌릴 수 없는 외부 행동(결제·전송·삭제)을 두지 말고, 두어야 한다면 다음 절의 멱등성으로 중복을 막아야 합니다(작성자 조언). 실행은 메모리 체크포인트로 했으며, 프로그램 종료 뒤에도 남기려면 파일·데이터베이스 같은 저장소의 체크포인트가 필요하다는 슬라이드의 단서는 이 실험이 보인 것이 아닙니다.

LangGraph 소스의 재시도 정책(RetryPolicy)은 max_attempts(“첫 시도를 포함해 포기하기 전까지 할 최대 시도 수”, 기본 3), retry_on(재시도할 예외 목록 또는 판정 함수), initial_interval(첫 재시도 전 대기, 기본 0.5초), backoff_factor(간격 배수, 기본 2.0), max_interval, jitter를 가집니다(슬라이드의 camelCase는 JavaScript 표기). max_attempts=3인 노드가 항상 실패하게 하자 총 3회 호출(첫 시도 포함) 뒤 오류가 났습니다. 이 ‘시도 수’와 앞 절의 ‘차례 수’(max_turns: 사용자 메시지·응답 한 쌍)는 세는 단위가 다릅니다. 슬라이드가 두 값을 구별하라고 한 이유입니다. 기본 retry_on은 모든 오류를 다시 시도하지 않습니다. 같은 정책(max_attempts=3)에서 연결 오류(ConnectionError)는 3회 호출, 입력 오류(ValueError)는 1회 호출로 끝나는 것을 실행으로 확인했습니다. 앞 표처럼 잘못된 요청·권한 오류는 다시 시도해도 해결되지 않으므로 어떤 오류를 재시도할지 정하는 것(retry_on)이 핵심입니다.

저장·실행 기반을 서비스로 제공받을 수도 있다(내가 정할 일: 목적과 작업 범위·사용할 자료·도구·완료 조건과 허용 행동 / 제공받을 수 있는 기반: 작업 상태 보존·코드를 실행할 공간·실행 기록과 일정 처리 — Managed Deep Agents, LangSmith 제공, 공개 베타). 관리형 실행의 비용 제한도 적용 범위를 읽는다(Claude Managed Agents · 세션: 작업 이력과 실행 환경을 이어 쓰는 단위): budget.max_list_cost(세션의 정가 기준 사용 비용 한도), stop_reason: budget_reached(예산 때문에 다음 요청이 보류된 상태), idle(작업 이력·실행 환경을 보존하며 대기). 진행 중 요청은 끝난다. 최종 비용이 한도를 넘을 수 있다.

확인 불가 · 관리형 실행의 제품과 비용 제한 항목 〔미확인〕

Managed Deep Agents(LangSmith, 공개 베타)와 Claude Managed Agents의 budget.max_list_cost·budget_reached 항목은 공식 안내에 접속할 수 없어 확인하지 못했습니다. 슬라이드가 밝힌 단서 “진행 중 요청은 끝난다. 최종 비용이 한도를 넘을 수 있다”는 한도가 ‘다음 요청의 보류’이지 ‘즉시 중단’이 아니라는 뜻이므로, 이 방식의 비용 제한은 한도 직전의 여유를 두고 설정해야 합니다(작성자 해석). 앞에서 본 것처럼 제한마다 세는 단위와 적용 시점(차례·시도·비용)이 다릅니다.

13오후 1 · 공개 변경 읽기 · 대기 안내를 서버 상태에서 화면 문구까지 연결한다 [p.53–56 · p.63–64 · p.67]

자료 p.53–56

같은 대화 서비스의 공개 변경(응답이 늦어질 때의 안내): 변경 전 — 응답 활동을 받기 전에도 “Thinking...” 표시, 변경 후 — 모델이 느리거나 이용하기 어려울 수 있음을 안내. 실제 구현에서 화면 문구를 고르는 조건: 요청 직후 Waiting… (응답 활동을 기다림) → 9초 뒤에도 대기(제공자의 모델 상태 조회) → 상태 저하로 반환(느리거나 이용하기 어려울 수 있다고 안내) / 응답 활동 도착(Thinking… 표시로 전환 · 예약 조회 취소). “이 변경은 기다리는 이유를 알린다. 모델 응답 자체를 빠르게 하지는 않는다.” 화면에서 보여 줄 것(답을 기다리는 중·계속 기다리는 중·모델 상태 저하 안내)과 서버에서 알 수 있는 것(요청을 시작한 시점·모델에서 온 응답 활동·제공자가 반환한 상태). 서버의 상태가 화면 문구가 되는 경로: 서버에서 상태 판단(route.ts → data-waiting-status 전송) → 화면 쪽에서 받기(use-active-chat.tsx → 상태 갱신) → 공유 상태로 보관(data-stream-provider.tsx) → 문구 표시(message.tsx → waitingStatus).

검증 · 대기 안내의 실제 구현과 슬라이드의 설명이 일치 〔p.54·p.56·p.67 정확히 일치〕

슬라이드의 설명이 실제 저장소와 단계·이름·값까지 같습니다. 9초(9000ms) 뒤에 제공자의 모델 상태를 조회하고(getModelAvailability), 결과가 impacted(영향을 받음)일 때만 ‘느리거나 이용하기 어려울 수 있다’는 안내로 바꾸며, 그 밖의 결과이거나 조회가 실패하면 ‘Still waiting…’으로 계속 기다립니다. 응답 활동이 도착하면 타이머를 취소하고 ‘Thinking…’으로 바꿉니다. 이것이 p.63의 “상태를 알 수 없음 → 계속 대기 · 장애라고 단정하지 않음”과 같습니다. 또 hasModelActivity가 참이면 thinking 외의 문구를 쓰지 않는 검사가 writeWaitingStatus 안에 있어, p.64의 “이미 응답 활동이 시작됐으면 뒤늦은 대기 안내는 쓰지 않는다”가 코드로 구현되어 있음을 확인했습니다. p.67의 변경(Thinking... 고정 문구 → waitingStatus?.message ?? "Waiting...")도 현재 message.tsx에 그대로 있습니다. 슬라이드가 말하듯 이 변경은 기다리는 이유를 알릴 뿐 모델 응답을 빠르게 하지는 않습니다.

자료 p.63–64 · 확인한 범위와 늦게 도착한 정보

상태 처리 코드를 서로 다른 순서로 확인했다(시간·모델 상태 응답은 가상 값): 9초 전 응답 활동 → 대기에서 응답 시작으로, 예약 조회 취소 / 9초 뒤 상태 저하 → 모델 상태 안내 / 응답 뒤 늦은 조회 → 응답 시작 표시 유지 / 상태를 알 수 없음 → 계속 대기, 장애라고 단정하지 않음. 확인한 범위는 상태 처리 로직이다. 늦게 도착한 정보가 화면을 되돌리지 않도록 같은 요청에서 두 처리의 결과가 도착하는 순서는 달라질 수 있다(① 상태 조회 시작 → ② 응답 활동 도착 → ③ 조회 결과 도착: 이미 시작했으므로 표시하지 않음). “실제 조건: 이미 응답 활동이 시작됐으면, 뒤늦은 대기 안내는 쓰지 않는다.”

보충 · ‘도착 순서’가 바뀌어도 화면이 올바르게 하는 처리

같은 요청에서 응답 활동과 상태 조회 결과가 어느 쪽이 먼저 올지는 정해져 있지 않습니다. 조회 결과가 늦게 와서 이미 시작된 응답 화면을 ‘모델이 느립니다’로 되돌리면 잘못된 안내가 됩니다. 그래서 ‘이미 응답이 시작됐는지’를 먼저 확인하고 늦은 결과를 버리는 조건이 필요하며, 이 조건은 시간이 걸리는 두 처리가 서로 다른 순서로 끝나는 경우를 모두 확인해야 비로소 검증됩니다(p.63이 네 가지 순서로 확인한 이유). 슬라이드가 밝히듯 이 확인은 상태 처리 로직에 한정되고, 실제 화면과 모델 연결의 동작까지 확인한 것은 아닙니다. 슬라이드의 9초 이후의 시간과 모델 상태 응답은 가상 값입니다.

기능 추가·변경 (p.57) 리팩토링
바꾸는 것 사용자가 할 수 있는 일이나 결과 내부 코드 구조 (겉으로 드러나는 동작은 유지)

둘은 목적이 다르므로 섞어서 한꺼번에 하지 않는 것이 안전합니다. 한 번에 두 가지를 바꾸면 동작이 달라졌을 때 어느 쪽 때문인지 가리기 어렵습니다(작성자 조언). 7일차 p.78·p.98의 ‘요청한 범위를 벗어난 변경은 없는가’와 ‘같은 조건에서 다시 비교’가 같은 취지입니다.

자료 p.58–60

화면에 보이는 결과까지의 연결을 읽는다(화면 입력 → 요청 전송 → 서버 처리 → 응답 반환 → 응답 읽기 → 결과 표시, 서버를 사용하는 웹 기능의 예·실제 구성에 있는 처리만 따라간다). 브라우저와 서버의 실행 기록은 읽는 곳이 다르다: Console(브라우저가 남긴 메시지·오류), Network(보낸 요청·받은 응답·걸린 시간), 서버 쪽 기록(서버 안에서 수행한 처리·오류). 서버 내부 기록은 서버에서 따로 읽고, 브라우저 오류만으로 원인을 확정하지 않는다. 요청 하나를 선택해 주소와 응답을 읽는다(① 목록에서 요청 선택 ② Headers 탭: 주소·요청 방식·상태 ③ Response 탭: 받은 내용을 읽는 곳, Chrome 공식 화면).

7일차 p.60의 ‘오류가 난 위치에 따라 확인할 화면이 다르다’와 같은 읽기입니다. 오늘 더해진 것은 Network 탭에서 요청 한 건을 골라 주소·상태·응답을 읽는 순서와 ‘브라우저 오류만으로 원인을 확정하지 않는다’는 단서입니다. 화면의 오류가 서버의 오류를 그대로 보여 주는 것은 아니므로(서버가 보낸 응답 코드·내용을 Network에서 읽고, 서버 내부는 서버 기록에서 읽음) 두 곳을 따로 봅니다. Chrome 개발자 도구의 화면 구성은 공식 안내에 접속할 수 없어 확인하지 못했습니다.

자료 p.61–62 · 브라우저 조작 기록

Playwright는 브라우저 조작과 확인을 자동으로 수행할 수 있는 도구다. Trace Viewer에서는 저장된 조작을 고르고 그때의 화면·요청·응답·오류를 함께 읽는다. 기록에 남은 범위에서 동작을 설명할 수 있다. 조작을 고르면 그 전후 화면이 보인다(① 조작 선택 ② 전후 화면 ③ 기록 탭: 왼쪽 조작 → 가운데 전후 화면 → 아래 기록 탭, 공식 도구 소개 화면).

검증 · Playwright Trace Viewer의 기능 (공식 저장소) 〔p.61–62 일치〕

Playwright 공식 저장소의 문서는 Trace Viewer를 “테스트의 기록된 추적을 탐색하는 GUI 도구로, 테스트의 각 동작을 앞뒤로 넘기며 그 시점에 무슨 일이 일어났는지 시각적으로 볼 수 있다”고 설명하고, 동작을 하나씩 선택하거나 타임라인에 올려 동작 전후의 페이지 상태를 보고 로그·소스·네트워크·오류·콘솔을 살필 수 있다고 적습니다. README는 ‘각 동작, DOM 스냅샷, 네트워크 요청, 콘솔 메시지를 Trace Viewer에서 확인’한다고 밝힙니다. 슬라이드의 ‘조작 선택 → 전후 화면 → 기록 탭’과 같습니다. 이 챗봇 템플릿 저장소에도 Playwright 설정 파일(playwright.config.ts)이 있어 같은 도구로 사용 과정을 확인하는 구성임을 확인했습니다. ‘기록에 남은 범위에서만 설명할 수 있다’는 슬라이드의 단서는 기록하도록 설정하지 않은 조작은 볼 수 없다는 뜻입니다(README의 예에서도 추적 기록은 설정(trace: 'on-first-retry' 등)에 따라 남습니다).

“회귀 확인은 단위·통합·전체 사용 검사에 함께 적용할 수 있다.” 앞의 세 가지는 범위(얼마나 큰 단위를 보는가)로, 회귀는 목적(전에 되던 것이 계속 되는가)으로 나눈 것이라 서로 겹칩니다. 앞의 대기 안내 변경에서도 새 문구(변경)가 나오는지와 기존의 정상 응답 표시가 유지되는지(회귀)를 함께 확인해야 합니다.

자료 p.66–70

변경 전후 파일을 AI와 읽으며 이유를 배운다(“문구를 바꾸는데 왜 서버도 수정했는지 설명해줘.” “응답이 먼저 오고 상태 조회가 늦게 오면 어떻게 돼?” “내 서비스에서 같은 목적을 더 간단히 이룰 방법은?”). 고정 문구를 상태에 따라 바뀌는 문구로 바꿨다(message.tsx: Thinking... → waitingStatus?.message ?? "Waiting..."). 설계 문서와 현재 코드가 다르면 먼저 차이를 읽는다(설계 문서는 만들려던 것, 현재 코드는 실제로 구현된 것을 보여 준다. 작은 변경이 쌓이면 둘의 구조가 달라질 수 있다. AI와 문서·파일을 함께 읽고 차이와 영향을 찾는다. 변경 이유는 작업 기록과 결정한 사람에게 확인한다). 기능 변경은 현재 구조와 대안을 함께 보고 정한다(현재 구조에서 가능한 방법은? 더 작은 변경으로 같은 목적을 이룰 수 있는가? 변경 뒤에도 유지해야 할 동작은?). 변경 범위를 나누고 동작을 확인하며 다음으로 간다(먼저 정할 것: 바꾸려는 동작·계속 유지할 동작 → 한 부분의 변경 범위 정하기 → AI와 해당 파일 변경하기 → 파일과 실제 동작 대조하기).

p.66의 첫 질문 “문구를 바꾸는데 왜 서버도 수정했는지”의 답은 앞 절의 경로에 있습니다. 화면은 서버가 알아낸 상태(모델 상태 조회 결과)를 모르기 때문에 서버가 상태를 판단해 data-waiting-status로 보내야 화면이 문구를 바꿀 수 있습니다(p.55의 “서버가 알아낸 상태를 화면에 전달해야, 상황에 맞는 안내를 할 수 있다”). 하나의 겉보기 변경(문구)이 서버·전달 경로·공유 상태·화면의 네 곳에 걸치는 이유입니다. p.68의 ‘설계 문서와 코드의 차이는 먼저 읽고, 변경 이유는 기록과 사람에게 확인한다’는 코드만 보고 이유를 추측하지 말라는 뜻입니다(작성자 해석).

자료 p.71–73 · 설정과 비밀

설정 예시는 비밀 값 대신 필요한 이름을 알려 준다(Vercel Chatbot의 설정 이름 발췌 · 별표는 실제 값 생략 표시: AUTH_SECRET=****(인증용 비밀 값) · AI_GATEWAY_API_KEY=****(모델 접근 키) · POSTGRES_URL=****(데이터베이스 주소)). 환경 변수는 프로그램이 읽는 설정의 이름과 값이다(코드가 읽는 이름 API_URL ↔ 그 환경에 설정한 값 접속할 서버 주소, 같은 코드라도 제공받는 값에 따라 연결되는 서버가 달라질 수 있다). Vercel: 일반 설정(Config: 권한 있는 구성원이 저장한 값을 다시 읽을 수 있다)과 비밀 설정(Secret: 저장 뒤 값을 숨긴다, 키·비밀번호 등에 사용). 비밀 값을 화면 코드·응답·공개 기록으로 보내지 않도록 구성한다.

검증 · 설정 이름은 실제 저장소와 같고, 비밀은 서버 쪽에 둔다 (7일차의 연장) 〔p.71 일치〕 〔Vercel의 일반·비밀 설정 화면은 미확인〕

템플릿의 .env.example에는 슬라이드가 보인 세 설정 이름이 **** 값으로 들어 있어 ‘예시 파일에는 이름만 두고 실제 값은 두지 않는다’는 방식이 확인됩니다. 7일차 오후 첫 02절에서 Next.js 공식 문서로 확인한 대로, 접두사가 없는 환경 변수는 서버에서만 읽히고 브라우저로는 전달되지 않으므로 이 세 값(인증 비밀·모델 접근 키·데이터베이스 주소)은 서버 쪽 설정이어야 합니다. Vercel의 일반 설정(Config)과 비밀 설정(Secret)의 구분, 저장 뒤 값을 숨기는 동작은 Vercel 공식 안내에 접속할 수 없어 확인하지 못했습니다.

자료 p.74–76 · 배포와 설정 반영

수정한 코드를 사용자가 쓰려면 배포가 필요하다(내가 편집한 코드: 변경 파일을 저장·동작을 확인 / 사용자에게 제공 중인 배포: 배포한 버전의 코드 실행·그 환경의 설정으로 연결·방문 주소에서 사용). 배포는 프로그램을 사용자가 접속할 환경에 제공하는 일이다. 미리보기(Preview: 변경한 기능을 확인할 배포, 검토할 사람에게 제공)는 검토용, 운영 배포(Production: 실제 사용자에게 제공할 배포, 운영 주소와 연결)는 실제 사용용이다. “같은 데이터베이스에 연결하면 미리보기에서도 운영 데이터를 바꿀 수 있다.” 설정은 적용 환경을 고른 뒤 새 배포에 반영한다(Vercel: 이름·값 → 적용 환경 선택 → 저장 → 바꾼 설정으로 다시 배포 → 실제 배포에서 연결된 대상을 확인). “이름과 값만 맞아도 현재 서비스에 바로 반영되는 것은 아니다.”

주의 · 미리보기가 운영 데이터를 바꿀 수 있다 (p.75)

미리보기는 ‘검토용’이라고 안심하기 쉽지만, 설정(환경 변수)이 운영과 같은 데이터베이스 주소를 가리키면 미리보기에서 한 저장·삭제가 실제 운영 데이터에 반영됩니다. 그래서 환경별로 다른 데이터베이스 주소(미리보기용·운영용)를 설정하는 것이 안전하고, 앞 절의 ‘적용 환경을 고른다’가 이 구분을 위한 선택입니다. 이는 7일차 p.79–80의 ‘파일을 되돌려도 외부 데이터는 되돌아가지 않는다’와 같은 종류의 위험입니다. Vercel의 환경 구분 화면은 공식 안내에 접속할 수 없어 확인하지 못했고, 위 위험은 설정의 논리에서 나오는 일반 설명입니다(작성자 해석).

자료 p.77–80

이 템플릿은 배포 전에 데이터베이스도 준비한다(실제 package.json의 build 항목: tsx lib/db/migrate && next build → ① 마이그레이션: 데이터베이스에 연결해 필요한 구조 변경 적용 ② 앱 빌드: 화면·서버 코드를 배포할 형태로 준비. 같은 코드라도 연결할 저장소와 권한이 없으면 이 준비 과정부터 막힌다). 배포 주소에서 대화 한 번을 끝까지 따라간다(방문 주소 열기: 접근 가능한가·원하는 배포 버전인가 → 질문 보내기: 사용자 확인·입력 저장·모델 인증 → 답 기다리고 읽기: 대기 안내 → 모델 응답 → 화면 표시 → 대화 다시 열기: 완성 메시지가 저장·조회되는가). 공유할 주소와 접근 권한을 함께 정한다(프로젝트를 편집할 사람과 서비스를 사용할 사람은 다를 수 있다). 모의 응답(미리 정한 값을 돌려줌: 화면 표시와 분기 등을 안정된 조건에서 살핌)과 실제 연결(해당 환경으로 요청을 보냄: 인증·입력·응답과 전체 기능을 함께 살핌)로 확인하는 것은 다르다.

검증 · 빌드 명령이 데이터베이스 준비를 포함한다 〔p.77 정확히 일치〕

템플릿의 package.json에서 "build": "tsx lib/db/migrate && next build"를 확인했습니다. &&는 앞 명령이 성공해야 뒤 명령이 실행된다는 뜻이므로, 마이그레이션이 데이터베이스 연결 부족(POSTGRES_URL 누락)으로 실패하면 앱 빌드까지 가지 못하고 배포가 멈춥니다(슬라이드의 “이 준비 과정부터 막힌다”). 배포 로그에서 빌드 실패를 읽을 때 ‘코드 오류’로만 보지 말고 먼저 마이그레이션 단계의 연결·권한을 확인해야 하는 이유입니다. 7일차 p.54–56의 ‘설치와 실행은 다르다·실행 명령은 package.json에서 확인’의 연장입니다. 모의 응답과 실제 연결의 구분은 8일차 p.62–64에서 본 ‘모델 입력과 응답을 직접 보고 확인한다’와 같은 취지입니다.

자료 p.81–83 · 롤백과 리믹스

롤백은 이전 배포를 다시 제공하는 조치다(현재 배포 → 되돌릴 배포 선택 → 운영 주소가 이전 배포를 제공, 공식 화면 · 코드와 외부 자료를 되돌리는 범위는 다르다). 이전 코드도 현재 데이터와 함께 동작해야 한다(이전 배포 다시 제공 / 현재 데이터·외부 서비스는 별도 상태로 남음). “배포를 되돌려도 저장된 자료가 자동 취소되지는 않는다. 이전 코드가 현재 자료·설정과 맞는지 확인한다.” 리믹스는 프로젝트의 독립된 복사본을 만든다(Lovable에서 복사되는 것: 코드·데이터베이스 구조·추가한 비밀 설정의 이름 / 새로 준비할 것: 실제 데이터·비밀 값·외부 연결·게시 상태).

검증 · 코드를 되돌려도 데이터는 그대로이고, 이전 코드와 현재 데이터가 맞아야 한다 〔7일차 실행으로 확인〕 〔보충〕 〔Lovable·Vercel 화면 미확인〕

7일차 오후 첫 05절에서 코드를 이전 상태로 되돌려도 외부 데이터(주문 2건)가 그대로임을 직접 실행으로 확인했습니다. 롤백이 이 경우와 같은 구조입니다. 여기서 더 나아가 이전 코드가 현재 데이터 구조와 맞는지가 문제가 됩니다. 새 배포의 마이그레이션이 데이터베이스 구조를 이미 바꿨다면(예: 열 추가·삭제) 이전 코드는 새 구조에서 오류를 낼 수 있고, 슬라이드의 “이전 코드가 현재 자료·설정과 맞는지 확인한다”가 이 위험을 가리킵니다(작성자 해석). 리믹스에서 ‘코드·데이터베이스 구조·비밀 설정의 이름’만 복사되고 ‘실제 데이터·비밀 값’이 복사되지 않는 구분은 앞의 .env.example(이름만 있고 값은 ****)과 같은 원리입니다. Lovable의 리믹스 동작과 Vercel의 롤백 화면은 공식 안내에 접속할 수 없어 확인하지 못했습니다.

19오후 2 · 기능을 늘리는 것과 도움이 커지는 것은 다르다 · 개선의 근거 찾기 [p.88–91]

자료 p.88–91

“다음에 뭘 만들지”보다 “무엇이 문제인지”를 먼저 찾는다(처음 해결하려던 일은 무엇이었나? 실제 사용자는 어디에서 도움을 얻거나 막히나? 다른 기술이나 더 간단한 방식으로 나아질 수 있나?). 실제 사용과 다른 해결법에서 개선의 근거를 찾는다(내 서비스를 쓰는 사람: 쓰는 과정을 보고 막히는 곳과 이유를 듣고 피드백 폼·연락 경로를 마련 / 비슷한 문제의 다른 해결법: 실제 리뷰·사례에서 방법을 찾고 AI와 기술·현재 구조를 살피며 다른 해결 가능성을 공부). “다른 제품의 리뷰와 AI의 추측은 내 서비스 사용자의 반응과 구별한다.” 사용 중 겪는 어려움에 따라 개선할 곳이 달라진다(진행 상황을 모름 → 상태·오류 안내 / 첫 응답까지 오래 걸림 → 모델·입력·앞단 처리의 시간을 비교 / 답이 일을 돕지 못함 → 질문·근거 자료·출력 내용과 사용 목적을 비교). 무엇을 개선하려는지에 따라 읽을 자료가 달라진다(원하는 일을 해냈는가: 사용 목적·실제 결과·이용자의 의견 / 어디에서 오래 걸렸는가: 시작·종료와 처리별 실행 기록 / 바꾼 것이 도움이 됐는가: 변경 조건과 이전·이후 결과 / 다른 방법은 없는가: 다른 해결 사례·최신 기술·현재 서비스 구조).

7일차 오전의 ‘기능을 정했다고 목적이 정해진 것은 아니다’(p.6)와 ‘배달 앱 대신 맛있던 가게를 다시 찾기’(p.11–12)가 서비스를 쓰는 단계에서 되풀이됩니다. 기능을 더하는 것보다 ‘어디서 막히는가’를 먼저 찾으면, 앞 절의 대기 안내처럼 작은 변경(진행 상황을 알림)이 같은 문제를 더 싸게 풀 수 있습니다. 세 가지 어려움(모름·느림·도움이 안 됨)은 개선할 곳이 서로 다릅니다. 같은 ‘느리다’는 호소도 응답 시간을 줄이는 변경이 아니라 안내를 바꾸는 변경으로 풀릴 수 있습니다(앞 절의 사례가 ‘기다리는 이유를 알릴 뿐 응답을 빠르게 하지는 않는다’). 다만 이것이 사용자에게 도움이 됐는지는 실제 사용자의 반응으로 확인해야 하며, 다른 제품의 리뷰나 AI의 추측으로 대신할 수 없습니다(p.89).

31핵심 정리

오전

  • 작업 루프는 계획 → 실행 → 결과 읽기 → 다음 행동의 반복이며, 다음 행동은 수정뿐 아니라 추가 조사·질문일 수 있습니다.
  • ‘반복이 끝났다’와 ‘결과가 좋다’는 독립이고, 검증 게이트는 통과 기준을 먼저 정해야 합니다. 정답을 모르는 채 스스로 고치면 정답을 오답으로 바꿀 수 있습니다(기본 모델 오답→정답 4.6% 대 정답→오답 15.8%).
  • 완료 조건(언제 끝났나)과 실행 제한(차례·시간·비용·권한)은 따로 정하며, 제한에 걸린 종료는 완료가 아니라 중단입니다.
  • 사람이 읽는 진행 문서와 프로그램이 저장하는 실행 상태를 둘 다 남깁니다. LangGraph에서는 재개하면 노드가 처음부터 다시 실행되어 중단 전 외부 행동이 반복되고(1회 → 2회), 다른 thread_id는 별도 흐름입니다.
  • 응답이 없어도 외부 행동은 끝났을 수 있으므로 멱등성(같은 작업 식별자)으로 안전하게 재시도하고, 재시도의 ‘시도 수’(첫 시도 포함)와 SDK의 ‘차례 수’는 세는 단위가 다릅니다.

오후 1

  • 기능을 바꾸려면 그 일을 맡은 호출(조회·구성·생성·저장)을 코드에서 먼저 찾고, 화면 → 요청 → 서버 → 응답 → 표시의 경로를 따라 읽습니다. 실제 챗봇 저장소의 파일·호출·설정이 슬라이드와 정확히 같았습니다.
  • 대기 안내는 서버가 알아낸 상태를 화면에 전달해야 바뀌며(9초 뒤 상태 조회, data-waiting-status), 모델 응답을 빠르게 하지는 않습니다. 늦게 도착한 정보가 화면을 되돌리지 않도록 도착 순서를 모두 확인합니다.
  • 기능 추가와 리팩토링은 목적이 다르고, 테스트는 범위(단위·통합·전체)와 목적(회귀)으로 나뉩니다. 브라우저 오류만으로 원인을 확정하지 않고 Network·서버 기록·Trace를 따로 읽습니다.
  • 설정은 이름만 공유하고 값은 환경별로 두며, 비밀은 서버 쪽에 둡니다. 설정은 새 배포에 반영해야 하고, 미리보기가 같은 데이터베이스를 가리키면 운영 데이터를 바꿀 수 있습니다.
  • 빌드 명령에 마이그레이션이 앞서므로 데이터베이스 연결이 없으면 빌드까지 못 갑니다. 롤백은 코드만 되돌리며 데이터는 그대로이고, 이전 코드가 현재 데이터 구조와 맞는지 확인해야 합니다.
