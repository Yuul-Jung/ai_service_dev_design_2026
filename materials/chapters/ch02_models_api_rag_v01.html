오전 — 모델은 누가 실행하고, 어떤 통로로 이용하는가

가중치와 실행 자원, 세 가지 이용 경로, 라이선스와 서비스 조건을 구분하고, 모델 카드·추론형 모델·멀티모달·벤치마크를 실제 자료로 읽는 방법을 정리합니다. 강의 음성 기록을 반영해 로컬 실행 시연, 중계 서비스, 가격–지능 그래프를 더했습니다.

  • 가중치 Weights 학습으로 조정한 수치를 담은 파일입니다. 받기만 해서는 쓸 수 없고, 실행 프로그램과 컴퓨터가 함께 필요합니다(p.6–7).
  • API Application Programming Interface 프로그램끼리 정해진 방식으로 요청과 결과를 주고받는 접점입니다. 사람은 화면으로, 프로그램은 API로 모델을 씁니다(p.10).

오후 첫 구간 — 요청과 응답을 읽고, 후보를 비교한다

API 요청에 담는 정보와 응답에 돌아오는 정보를 실제 필드 이름으로 따라가고, 같은 회의 메모로 두 후보의 결과·시간·비용을 비교합니다. 강의 음성과 화면 캡처를 반영해 인증·요청 요소·도구 루프·상태 페이지·검색·서비스 비용을 더했습니다.

  • 사용량 Usage 응답이 보고하는 입력·출력 토큰 수입니다. 비용은 출력 한도가 아니라 이 값에 단가를 곱해 계산합니다(p.61).
  • 스트리밍 Streaming 응답을 조각으로 나눠 받는 방식입니다. 첫 내용이 빨리 보일 뿐 완료 시각은 같습니다(p.62–63).

오후 둘째 구간 — 입력을 바꿀 것인가, 모델을 바꿀 것인가

프롬프팅·검색 증강 생성·미세조정이 각각 무엇을 바꾸는지 행사 안내 예로 구별하고, 클라우드·운영 주체·접근 권한·약관의 학습 이용과 기록 보존 조항을 따로 읽는 방법을 정리합니다.

  • 검색 증강 생성 RAG 질문으로 관련 자료를 찾아 입력에 넣고, 기존 모델이 그 자료를 근거로 답하게 하는 구성입니다(p.90). 모델은 바뀌지 않습니다.
  • 미세조정 Fine-tuning 학습 예로 매개변수를 추가 조정해 이후 응답 행동을 바꿉니다(p.94). 바뀌는 사실을 알려 주는 데는 맞지 않습니다.

마지막 구간 — 학습자가 따라 할 수 있는 이용 안내 만들기

접속·요청·결과 확인의 순서를 안내로 쓰고, 20명이 10번씩 쓰는 수업의 비용과 동시 사용 한도, 오류가 났을 때 먼저 확인할 곳을 정리합니다.

  • 요청 빈도 제한 Rate limit 일정 시간 동안 처리할 수 있는 요청 수의 상한입니다. 총비용과 별개로 수업 진행 속도를 정할 수 있습니다(p.114–115).
  • 비용 알림 Budget alert 설정한 지출 상태를 알려 주는 기능입니다. 알림만으로는 이용이 멈추지 않습니다(p.115).

강의에서 덧붙인 말 〔강의〕

강사는 첫머리에서 “새로운 모델이 나올 때마다 계속 공부해야 한다”고 강조했습니다. 어떤 모델이 무엇에 강하고 약한지에 대한 감각을 예민하게 키우는 것이 목표이고, 그 출발점이 모델 카드에서 정보를 찾는 일입니다(07절).

전날 내용의 복습으로는 ‘규칙 기반 전문가 시스템 → 머신러닝 → 딥러닝·인공신경망 → LLM’의 흐름, ‘모델은 사고하는 뇌를 가상으로 만든 덩어리이며 모델만으로는 아무것도 못 한다’, 입력이 토큰화되어 계산층을 거쳐 다음 토큰을 순서대로 만든다는 과정, 온도(낮추면 확신하는 답, 높이면 다양한 답), 매개변수, 답변 전에 생각 토큰을 먼저 만드는 추론을 짚었습니다. 1일차 자료의 p.24, p.59, p.74–77, p.116, p.123에 해당합니다.

또 지금 쓰는 채팅 앱은 AI 회사가 만든 서비스의 일부일 뿐이라고 했습니다. AI를 제대로 쓰려면 모델을 고르고 접속하는 방법(API·로컬 실행)과 비용·운영을 알아야 한다는 것이 오늘의 출발점입니다.

※ 강의 음성은 AI가 자동으로 받아 적은 글이라 모델명·숫자에 인식 오류가 많습니다. 뜻이 분명한 내용만 옮겼고, 모델명과 수치는 단정하지 않았습니다.

AI를 처음 배우는 사람에게 가장 좋은 수업은 학습자가 매일 반복하는 자기 업무를 AI로 바꿔 보게 하는 것이라고 했습니다. 개념부터 가르치지 않고 학습자의 일에서 출발하면, 오늘 배우는 입력·모델·이용 경로가 곧바로 자기 업무와 연결됩니다.

보충 · 자료 밖 내용

공개 가중치를 내 컴퓨터에서 실행할 때 쓰는 실행 프로그램으로는 Ollama, llama.cpp, vLLM, Hugging Face Transformers 등이 널리 알려져 있습니다. 같은 가중치라도 어떤 실행 프로그램과 장치를 쓰느냐에 따라 속도와 필요한 메모리가 달라집니다. 05절에서 공식 측정값으로 확인합니다.

강의에서 덧붙인 말 · 가중치와 실행 환경 〔강의〕

강사는 매개변수를 “입력이 들어올 때 어떻게 연산할지에 대한 수많은 계산 값”으로 풀고, 그것을 모두 모은 모델 전체의 수치 데이터를 가중치 데이터라고 했습니다. 공개 모델이라면 “모델을 쓴다 = 가중치 데이터를 내려받는다”고 볼 수 있다고 했습니다.

실행에는 가중치(숫자 덩어리)와 이를 읽어 계산하는 프로그램이 필요하고, 램은 가중치를 올려 두는 공간, GPU는 계산하는 장치입니다. CPU로도 계산은 되지만 그동안 컴퓨터가 멈춘 듯 느려져서, 웬만하면 GPU가 있는 편이 낫다고 했습니다. 직접 돌려 본 과정은 06절에 정리했습니다.

강의에서 덧붙인 말 · “가중치를 직접 고쳤다”는 기사 〔강의〕

강사는 오후 수업을 열며 최근 기사를 하나 소개했습니다. 한 AI 회사가 자사 모델을 이용해 아주 작은 공개 모델(0.8B급)의 매개변수를 읽고 가중치를 직접 고쳐서 문제 풀이 점수를 크게 올렸다는 내용입니다. 강사의 요점은 “매개변수는 학습하면서 자동으로 만들어지는 것이라 사람이 읽고 이해해 직접 고치는 것은 거의 불가능에 가깝다”이고, 이 기사는 모델이 작아서 가능했던 예외로 소개한 것입니다. 사람의 뇌에서 뉴런을 하나하나 분석하기는 불가능하지만 초파리 뇌는 전부 분석했다는 비유도 곁들였습니다.

확인 불가: 기사의 회사·모델 이름·점수 향상 폭은 음성 기록이 불분명하고 이 환경에서 확인하지 못했습니다. 작성자가 아는 범위에서는 모델 내부를 해석하려는 연구 분야(해석가능성)가 있고 작은 모델에서 시도되며, 초파리 뇌 전체의 연결 지도는 2024년에 공개된 것으로 압니다(작성자 지식, 미확인). 수업에서 사실로 전하려면 출처를 먼저 확인하세요. 이 기사가 맞더라도 “큰 상용 모델의 가중치를 사람이 직접 고칠 수 있다”는 뜻은 아닙니다(03절).

03오전 · 세 가지 이용 경로 [p.9–12]

① 제공자의 서비스 화면 (p.9)

처리 흐름: 사용자가 화면에 입력 → 제공자가 모델 실행 → 제공자가 운영하는 화면에서 응답 확인

② API로 내 프로그램에서 (p.10–11)

처리 흐름: 내 프로그램의 요청 (모델과 입력을 지정) → 외부 제공자의 모델 실행 → 내 프로그램이 응답 사용

자료 p.10–11

API는 프로그램끼리 정해진 방식으로 요청과 결과를 주고받는 접점이다. “프로그램이 실행되는 곳과 모델이 실행되는 곳은 다를 수 있다.”

③ 공개 가중치로 직접 실행 (p.12)

처리 흐름: 모델 가중치 확보 → 실행 프로그램과 컴퓨터 준비 → 모델 실행과 이용 화면 연결

자료 p.12

“실행·접근 권한·기록·업데이트를 자신이나 조직이 관리한다.”

강의 포인트

세 경로를 “누가 컴퓨터를 켜 두고 있는가”로 설명하면 쉽습니다. ①과 ②는 제공자의 컴퓨터가 계산하고, ③은 내 컴퓨터나 조직의 컴퓨터가 계산합니다. ①과 ②의 차이는 계산하는 곳이 아니라 사람이 쓰느냐, 프로그램이 쓰느냐입니다.

강의에서 덧붙인 말 · 채팅 화면은 껍데기, API는 직접 쓰는 통로 〔강의〕

강사는 채팅 프로그램을 “누가 만들어 놓은 것이고, AI 자체가 아니라 AI를 쓸 수 있는 껍데기”라고 했습니다. 껍데기 없이 모델을 직접 가져다 쓰려면 API를 씁니다. 같은 모델을 화면으로 쓸 수도, API로 쓸 수도 있다는 점이 p.9–11의 요점입니다.

시연에서는 LM Studio의 로컬 서버 기능을 보여 주었습니다. 내 컴퓨터에 올려 둔 모델에 API 서버를 열어 두면, 채팅창 없이도 다른 프로그램이 필요할 때마다 그 모델을 불러 쓸 수 있습니다. 외부 모델 API를 쓰는 것(p.11)과 같은 구조이고, 모델이 도는 컴퓨터가 내 것이라는 점만 다릅니다.

보충 · 자료 밖 내용 〔공식 문서 확인〕

LM Studio 공식 문서 저장소(lmstudio-ai/docs)에 “OpenAI Compatibility Endpoints” 항목이 있어, 로컬 서버가 널리 쓰이는 외부 API와 같은 형식(OpenAI 호환)을 제공함을 확인했습니다. 따라서 같은 프로그램에서 접속 주소만 바꿔 외부 모델과 로컬 모델을 번갈아 시험할 수 있습니다. 지원하는 항목의 범위는 쓰는 버전의 문서에서 확인하세요.

확인 불가 · 구독과 API 크레딧 〔미확인〕

강사는 월 100달러 이상 구독하면 같은 금액의 API 크레딧을 받는다고 설명했습니다. 구독 요금제와 API 요금은 서로 다른 상품인 경우가 많고, 이런 혜택이 있는지와 조건은 서비스와 시기에 따라 달라서 제 쪽에서는 확인할 수 없었습니다. 수업에서 그대로 전하지 말고 각 서비스의 공식 안내에서 확인하세요(예: Claude 구독은 support.claude.com, API는 docs.claude.com).

보충 · 자료 밖 내용 〔용어〕

“공개 가중치(open weights)”와 “오픈소스”는 같은 말이 아닙니다. 오픈소스 이니셔티브(OSI)가 2024년에 발표한 오픈소스 AI 정의는 가중치뿐 아니라 학습 코드와 학습 자료에 관한 충분한 정보까지 공개되어야 오픈소스 AI로 봅니다(작성자 지식, 원문 미확인). 그래서 가중치만 공개한 모델은 흔히 “공개 가중치 모델”로 따로 부릅니다. 수업에서는 학습자가 “오픈소스니까 마음대로 써도 된다”고 말할 때 이 구분과 라이선스 확인을 함께 짚어 주세요.

강의에서 덧붙인 말 · 두 개의 서로 다른 기준 〔강의〕

강사는 설명 도중 “공개 가중치와 API는 서로 다른 기준이다”라며 앞의 설명을 스스로 정정했습니다. 공개 가중치의 반대는 비공개(상용 모델)이고, API의 반대는 채팅 서비스입니다. 둘은 다른 축이므로 2×2로 놓으면 섞이지 않습니다.

API (프로그램이 씀) 채팅 서비스 (사람이 씀)
비공개 가중치 Claude · GPT · Grok · Gemini 등 그 회사의 API 그 회사의 앱·웹
공개 가중치 Qwen · DeepSeek 등 외부 제공자의 API, 또는 내 PC의 로컬 서버 외부 서비스 화면, 또는 LM Studio 같은 내 PC의 화면

이 표는 자료 p.16의 세 조합과 같은 내용입니다.

상용 모델은 가중치를 볼 수 없어서 그 회사의 API(또는 앱)를 쓰는 것 외에 방법이 없다고 했습니다. 공개 모델도 GPU나 큰 메모리가 없으면 직접 돌릴 수 없으므로, 실행 환경을 대신 제공하는 서비스가 많고 그 서비스는 API로 씁니다. 강의에서는 DeepSeek의 API 플랫폼과 Qwen을 제공하는 클라우드 서비스를 예로 보여 주었습니다.

검증 · “상용 모델은 튜닝할 방법이 없다” 〔단순화 가능〕

상용 모델의 가중치를 내가 내려받아 직접 바꾸는 것은 불가능합니다. 다만 작성자가 알기로는 일부 제공자가 일부 모델에 대해 제공자가 대신 돌려 주는 미세조정 기능을 따로 제공합니다(작성자 지식, 이 환경에서는 확인하지 못함). 그래서 “방법이 전혀 없다”보다 “가중치를 받아 직접 바꿀 수는 없고, 제공자가 허용하는 범위에서만 가능하다”가 정확합니다. 수업에서는 후자로 말하고, 쓰려는 모델의 공식 안내를 확인하게 하세요. 미세조정 자체는 p.94–96에서 다룹니다.

강의에서 덧붙인 말 · OpenRouter 같은 중계 서비스 〔강의〕

모델이 너무 많아 하나씩 가입해 쓰기 불편해서, 여러 회사의 모델을 한곳에서 API로 쓰게 해 주는 중계 서비스가 생겼다고 했습니다. 강의에서 보여 준 서비스가 OpenRouter입니다(음성 기록에는 ‘오픈라우터’로 적힘).

  • 공개 모델은 누구나 내려받을 수 있어서, 같은 모델을 서비스하는 제공자(provider)가 세계 곳곳에 여러 곳 있습니다. 같은 모델이라도 제공자마다 가격이 다르므로 가장 싼 곳을 고를 수 있습니다.
  • 크레딧을 충전한 뒤 그 크레딧으로 API를 부르는 방식이고, 채팅 화면도 제공합니다.
  • 강사는 이를 이용해 전 세계 모델을 두루 시험해 보라고 권했습니다.

강의 안의 모순: 어떤 대목에서는 “Claude·GPT 같은 상용 모델은 이런 서비스가 필요 없다”고 했고, 다른 대목에서는 “상용 모델도 목록에 다 있다”고 했습니다. 작성자가 아는 바로는 상용 모델도 중계 서비스에 올라 있으며, 이 경우 제공자는 원래 회사 하나입니다(작성자 지식, 미확인). 공개 모델은 제공자가 여럿, 상용 모델은 원래 회사 하나라고 정리하면 두 말이 모두 맞습니다.

보충 · 자료가 지나가는 곳이 늘어난다

주의 · GB의 두 가지 뜻

자료는 1GB를 10억 바이트로 둡니다. 운영체제나 일부 도구는 1GB를 2³⁰ = 1,073,741,824바이트(정확히는 GiB)로 표시해서, 같은 파일이 약 7% 작은 숫자로 보일 수 있습니다. 학습자가 “계산과 다르다”고 하면 단위부터 확인하세요.

강사는 LM Studio로 공개 모델을 내려받아 자기 컴퓨터에서 직접 돌려 보였습니다. 01절의 “가중치 + 프로그램 + 램 + GPU”를 실제로 해 보는 과정입니다.

처리 흐름: 모델 검색 (크기가 함께 표시됨) → 내 PC에 맞는지 확인 (‘최적’ 표시 활용) → 내려받기 (가중치 파일) → 불러오기 (메모리에 올림) → 대화 (생각 과정 표시) → 로컬 서버 (다른 프로그램이 호출)

강의에서 보여 준 것 〔강의〕

  • 모델 크기가 화면에 표시됩니다. 수백 GB짜리 대형 공개 모델은 파일을 내려받을 수는 있어도 “그만큼의 메모리가 있어야 돌아가므로” 쓰기 어렵고, 쓰려면 1TB급 메모리의 PC나 그래픽 카드가 필요하다고 했습니다(음성 기록의 숫자: 약 554GB).
  • ‘최적’ 표시는 내 PC 사양을 읽어 돌아가는 모델 중 가장 좋은 것을 알려 준다고 했습니다.
  • 메모리가 작은 사람도 12B급 모델(6GB 안팎)이면 시험해 볼 수 있다고 했습니다(05절 검증과 부합).
  • 시연: 48GB 메모리의 맥에서 27B급 모델이 생각 과정을 보여 주며 한국어로 응답했습니다. 사고를 얼마나 깊게 할지도 설정할 수 있었습니다.
  • 도구: NVIDIA RTX 노트북은 LM Studio나 Ollama, 맥은 MLX 기반 도구, 윈도우는 GGUF 형식(음성 기록에는 ‘거프’로 적힘, 작성자의 추정) 모델을 많이 쓴다고 했습니다.

검증 · “PCI 슬롯이 제일 빠르다”는 설명 보완 〔보완 필요〕

강사는 윈도우 PC의 그래픽 카드가 가장 빠르다고 했습니다. 방향은 맞지만, 생성 속도를 좌우하는 것은 보통 PCI 슬롯이 아니라 가중치가 올라가 있는 메모리의 대역폭입니다(작성자 지식). 일반적으로 그래픽 카드의 전용 메모리가 가장 빠르고, 통합 메모리 기기는 그보다 느리다고 알려져 있습니다. 대략적인 상한은 이렇게 어림할 수 있습니다.

text

세 대역폭은 설명용 가정값입니다. 이 어림은 상한이고 실제는 더 낮습니다. 작은 모델에서는 아예 맞지 않습니다. 예를 들어 05절에서 본 Qwen2.5-0.5B 공식 측정은 대역폭이 매우 큰 A100에서도 Transformers로는 초당 47토큰에 그쳤고, 같은 모델을 vLLM으로 돌린 측정은 초당 311.55토큰이었습니다. 모델이 작으면 모델 파일을 읽는 시간이 아니라 실행 프로그램의 처리 지연 같은 다른 요인이 속도를 정하기 때문입니다. 전문가 혼합(MoE) 모델은 한 번에 일부 매개변수만 읽어서 다시 다릅니다.

검증 · 필요한 메모리는 파일 크기보다 크다

05절의 공식 측정에서 0.5B 모델은 입력이 거의 없을 때 0.97GB였지만 입력이 30,720토큰이면 2.34GB로 늘었습니다(+1.37GB). 모델 파일이 메모리에 들어간다고 끝이 아니라, 문맥 길이만큼 더 필요하고 운영체제와 다른 프로그램의 몫도 남겨야 합니다. 강사가 “32GB급 모델을 48GB 맥에서 돌리면 다른 게 버벅거렸다”고 한 경험과 맞는 설명입니다. 또 맥은 통합 메모리 중 GPU가 쓸 수 있는 비율에 기본 상한이 있는 것으로 알려져 있습니다(작성자 지식, 대략 3분의 2~4분의 3으로 기억하며 미확인). 정확한 값은 사용할 기기와 도구의 안내를 확인하세요.

강의 포인트 · 내 PC로 돌릴 수 있는지 확인하는 순서

  1. 모델 파일 크기를 확인한다 (또는 매개변수 수 × 비트 수 ÷ 8로 어림한다).
  2. 내 메모리(그래픽 메모리 또는 통합 메모리)가 파일 크기 + 문맥·운영체제 몫의 여유를 감당하는지 본다.
  3. 돌아가더라도 속도는 메모리 대역폭에 달려 있음을 안내한다.
  4. 모델 카드에서 라이선스와 허용 용도를 확인한다 (03절).
  5. 시험에는 공개용 예제만 쓴다. 내 PC에서 돌려도 외부 검색 같은 도구를 연결하면 자료가 밖으로 나갈 수 있다(p.99).

주의 · 정렬을 줄인 파생 모델

강사는 모델 이름 뒤에 ‘uncensored’가 붙은 파생 모델을 소개하며, 모델이 불법적인 일을 중간에 막지 못하도록 풀어 놓은 버전이라고 설명했습니다. 1일차의 정렬(p.100)을 약하게 만든 모델이라는 뜻입니다. 쓰는 사람이 책임져야 하는 영역이 커지므로, 라이선스·기관 규정·법적 책임을 먼저 확인해야 하고 수업 시연용으로는 권하지 않습니다. 강사는 또 중국 모델의 API가 한국사 문제에서 중단되는 경험을 했다고 했는데, 이는 모델이 아니라 제공자 쪽 필터일 수 있으며 원인은 확인할 수 없었습니다.

보충 · 자료 밖 내용

  • MMLU는 Hendrycks 등(2021, ICLR)이 제안한 평가로, 57개 과제의 객관식 문제로 이루어져 있습니다(p.45와 일치).
  • 5-shot은 문제 앞에 풀이 예시 다섯 개를 입력으로 넣는 설정입니다. 1일차 p.99의 “입력에 예시 제공하기”와 같은 방식이라, 설정이 다르면(0-shot 등) 같은 모델도 점수가 달라집니다.
  • 점수를 읽을 때 주의할 점: 시험 문제가 학습 자료에 섞여 들어가면 점수가 실제 능력보다 높게 나올 수 있습니다(오염, contamination). 상위 모델들의 점수가 모여 차이가 잘 드러나지 않는 포화 문제도 있습니다. MMLU 문항 일부에 정답 오류가 있다는 분석(예: MMLU-Redux)과, 더 어려운 변형(예: MMLU-Pro)도 나와 있습니다.

그래서 p.48의 결론처럼, 공개 점수는 후보를 좁히는 데 쓰고, 최종 선택은 내 자료로 직접 시험한 결과로 합니다.

강의에서 덧붙인 말 · 종합 지수와 가격–지능 그래프 읽기 〔강의〕

  • 종합 지능 지수. 강사는 AI의 지능을 수치로 측정해 보여 주는 지표(음성 기록에는 ‘AI 인텔리전스 인덱스’)를 소개하고 “IQ를 측정한 것”에 비유했습니다. 모델마다 점수가 있고, 이 지수는 최근 기준이 바뀌어 수치가 달라졌다고 했습니다. 판본이 다른 점수는 직접 비교할 수 없다는 p.44·p.47의 원칙과 같습니다.
  • 가격–지능 그래프. 가로는 가격, 세로는 지능입니다. 가격이 낮고 지능이 높은 쪽이 좋습니다. 그래프의 점선은 “같은 가격에서 가장 높은 지능의 모델을 이은 선”이고, 이 선 위의 모델은 “그 가격대에서는 지능 기준으로 가장 좋다”는 뜻입니다.
  • 그 밖의 순위. 문제 해결에 쓴 토큰량(적을수록 좋음), 비용, 출력 속도가 따로 있고, 공개 가중치·멀티모달·국가별로 거를 수 있습니다. 세부 지표로는 지식 노동 종합, 에이전트, 코딩 등이 있다고 했습니다.
  • 숫자 하나의 한계. 지능을 숫자 하나로 표현하면 너무 거칠므로 세부 지표를 하나씩 공부하라고 했습니다. 기업은 자기 모델이 잘 나온 지표를 골라 자랑하므로, 어디에 약한가도 함께 봐야 합니다. 모델 발표 자료의 지표 표를 캡처해 두고 무엇을 측정하는지 공부하라고도 했습니다.

강사의 결론은 분명했습니다. 이 지표들은 벤치마크를 만든 곳이 “이런 것을 측정하겠다”고 정한 공개 평가이고, 실사용과 다릅니다. “지표가 좋으니 좋다”는 것은 순진한 판단이고, 지표만 보고 AI를 고르는 것은 요즘 아무도 하지 않으며 강사 본인도 그렇게 하지 않는다고 했습니다. 모델은 인간의 사고를 모사한 것이라 어떤 명령에는 일을 잘하고 어떤 명령에는 못 하는지의 감각이 더 중요하고, 이는 직접 써 보고 내 과제에 적용해 보아야 얻습니다. 다양한 API를 써 보는 방법으로 앞의 OpenRouter를 권했습니다(03절).

이는 p.48의 “공개 평가로 아는 것 / 내 과제에서 더 볼 것” 표와 같은 결론입니다. 점수는 후보를 좁히는 데 쓰고, 최종 선택은 내 자료로 시험한 결과로 합니다.

확인 불가 · 강의 화면의 구체적 순위 〔미확인〕

강사는 당시 화면에서 가격대마다 최상위 모델이 달랐고(저가 구간은 GPT 계열, 최상위 구간은 Gemini·Claude 계열 등), 출력 속도는 Gemini 계열이 빠른 편이라고 말했습니다. 이는 그 시점 화면의 모습이고, 음성 기록의 모델명과 숫자가 크게 부정확해 옮기지 않았습니다. 지수를 내는 사이트 이름도 기록이 불분명합니다. 작성자는 Artificial Analysis의 Intelligence Index가 대표적이라고 알고 있지만 강의 화면과 같은 곳인지는 확인할 수 없었습니다. 이런 순위는 자주 바뀌므로 수업 직전에 해당 사이트를 직접 열어 보세요.

  • 키가 노출되었다면 바로 폐기하고 새로 발급합니다. 지운 커밋에도 기록이 남을 수 있으므로, 저장소에서 지우는 것만으로는 충분하지 않습니다.

인증 방식 어떻게 쓰는가 강사의 설명
계정 로그인 기반 클라우드 서비스에서 계정의 API 사용 권한을 설정하고, 인증된 계정을 바탕으로 API 사용을 허용 그 계정에 어떤 접속 권한을 줄지 서비스에서 규정으로 설정할 수 있다
키 값 기반 키를 만들어 두고, 그 키를 가진 쪽이 계정의 API를 쓰게 함 “정말 집 열쇠 같은 것”. 키 정보를 가지고 있으면 언제든 쓸 수 있다
  • 단기 액세스 토큰. 등록 절차를 거쳐 짧게 유효한 토큰을 발급받아 쓰는 방식이 있고, 고정된 API 키를 쓰는 것보다 안전하지만 “귀찮다”고 했습니다. 요즘은 API 보안이 중요한 문제라 알아 둘 필요가 있다는 말입니다.
  • 요청 한도. API 키 하나당 보낼 수 있는 요청 수에 제한이 있어서, 서비스에 1만 명이 몰리면 제한에 걸릴 수 있습니다. AI 서비스는 이 제한을 설계에 넣어야 합니다. 위 검증 상자(프로젝트 단위 한도)와 같은 이야기입니다.
  • 사용량 확인. API 사용량 모니터링과 크레딧 지출은 서비스의 콘솔 화면에서 확인할 수 있습니다.
  • 로컬은 다름. LM Studio처럼 내 컴퓨터에서 돌리면 API 권한 문제는 크게 신경 쓰지 않아도 되지만, 외부 모델을 쓰면 API 보안 설정의 개념을 알아야 합니다.

고정 키는 한 번 노출되면 폐기하기 전까지 누구나 쓸 수 있지만, 단기 토큰은 만료되므로 노출되어도 피해 기간이 짧습니다. 그래서 많은 클라우드는 서버 쪽에서는 계정 기반의 단기 토큰을, 간단한 시험에는 키를 쓰게 합니다. 어느 쪽을 쓰든 키와 토큰은 코드에 직접 쓰지 않고 환경 변수나 비밀 관리 기능에 둡니다. 강사가 시연한 콘솔 화면의 메뉴 이름은 음성 기록이 부정확해 옮기지 않았으니, 사용할 서비스의 현재 화면에서 확인하세요.

강의 화면 · 스트리밍에서 오는 조각의 종류 〔강의 화면〕

강사 화면의 문서는 스트리밍 응답이 여러 사건으로 나뉘어 오고, 조각(델타)의 종류가 다르다고 적었습니다.

조각 종류 담고 있는 것
text_delta 답변 문장의 일부
thinking_delta 사고 과정의 일부
input_json_delta 도구 입력의 일부. JSON 문자열이라 이어 붙여 해석해야 함
signature_delta 사고 과정에 붙는 서명

같은 화면에는 최대 출력 토큰(max_tokens)이 큰 요청은 HTTP 시간 초과를 피하려고 스트리밍을 쓰길 권장한다는 말도 있었습니다. 공식 Python SDK 소스는 이보다 강하게 예상 소요 시간이 10분을 넘을 수 있는 비스트리밍 요청에는 스트리밍이 필요하다(“Streaming is required for operations that may take longer than 10 minutes”)고 안내하고, max_tokens로 비스트리밍 요청의 예상 시간을 계산합니다. 앞의 “출력이 길수록 완료까지 오래 걸린다”와 이어지는 이유입니다. 위 다섯 가지 조각 종류는 SDK 타입 파일(text_delta, thinking_delta, input_json_delta, signature_delta, citations_delta)에서 모두 확인했습니다.

보충 · 자료 밖 내용

한도 초과나 일시 장애로 다시 시도할 때는 보통 간격을 점점 늘리며 재시도합니다(지수 백오프, exponential backoff: 1초, 2초, 4초…). 실패하자마자 같은 요청을 반복하면 한도를 더 빨리 소진하고, 장애 중인 서비스에 부담을 더합니다. 권한 오류나 형식 오류는 기다려도 해결되지 않으므로 재시도 대상이 아닙니다.

강의에서 덧붙인 말 · 한도 초과와 장애를 서비스가 처리해야 하는 이유 〔강의〕

강사는 한도 초과와 일시적인 서비스 장애를 항상 다뤄야 한다고 했습니다. AI는 사용량이 비싸서 크레딧을 충전해 두고 쓰는데, 크레딧이 소진되면 한도 초과로 동작이 멈춥니다. 서비스를 만들어 놓고 한도 초과를 처리하지 않으면 나중에 문제가 되고, 장애를 처리하지 않으면 사용자에게는 오류만 계속 뜨는 화면으로 보여 사용자 경험을 망친다는 것입니다.

또 응답이 제대로 끝나지 않았을 때 API가 돌려주는 종료 이유를 받아서, 그에 맞게 사용자에게 안내하거나 요청 설정을 고쳐야 한다고 했습니다(03절의 종료 정보, 1일차 p.121의 출력 한도 확인).

  • 이미지는 한 요청에 많이 넣을 수 있고(강사 설명은 최대 600장), 긴 변이 일정 크기(1568 픽셀)를 넘으면 자동으로 줄어들며, 너무 작은 이미지(약 200 픽셀 미만)는 잘 인식되지 않는다고 했습니다. 소모되는 토큰은 이미지 크기에 비례합니다.

이 제한은 모델·시기마다 바뀌는 값이고 서비스마다 다릅니다. 수업에서 숫자를 그대로 전하지 말고 쓰려는 모델의 현재 문서에서 확인하게 하세요.

출력 토큰 한도를 직접 관리해야 하는 이유

강의에서 덧붙인 말 〔강의〕

강사는 AI 코딩 도구가 “토큰을 아끼려고” 최대 출력 토큰을 작게 걸어 두는 경우가 있다고 했습니다. 그러면 결과가 한도에서 잘려서 원하는 결과가 안 나오고, 다시 한도를 늘려 호출하는 일이 벌어지므로, 최대 토큰은 사람이 직접 관리해야 하고 AI에게는 “토큰 제한은 풀어”처럼 지시하면 된다고 했습니다(코드를 직접 쓸 필요는 없음). 또 출력 토큰에는 사고 토큰이 포함되므로, 사고를 무조건 늘리는 것이 좋은 것만은 아니라고 했습니다.

강사가 예전에 어떤 서비스가 97% 수준이어서 “하루에 한 번은 무조건 장애가 났다”고 말한 것은, 하루 43.2분 중단이라는 계산과 대체로 맞습니다. 99.9%와 99.7%는 숫자로는 0.2%p 차이지만 한 달 중단 시간은 43분과 130분으로 세 배 가까이 벌어집니다.

주의 · 이 숫자를 읽을 때 〔보완〕

  • 상태 페이지의 가동률은 기간(최근 90일 등)과 구성 요소마다 다르게 집계됩니다. 서비스 전체의 숫자가 아니라 내가 쓰는 구성 요소(예: API)의 숫자를 봐야 합니다.
  • 강사가 화면에서 본 서비스별 수치와 비교는 그 시점의 모습이고, 음성 기록의 서비스 이름과 숫자가 부정확해서 옮기지 않았습니다. 수업 직전에 직접 열어 보세요.

가정: 20명이 각 10회 실행. 앞서 계산한 후보 가 사용(입력 100만 토큰당 1,000원, 출력 100만 토큰당 4,000원).

검증 · 수업 규모의 예상 비용 (p.112–113) 〔일치〕

text
요청 수   20명 × 10회               = 200회
입력      200회 × 1,000토큰          = 200,000토큰
출력      200회 × 200토큰            = 40,000토큰
입력 비용  200,000 ÷ 1,000,000 × 1,000원 = 200원
출력 비용   40,000 ÷ 1,000,000 × 4,000원 = 160원
총비용     200원 + 160원              = 360원

(교차 확인) 한 번 1.8원(p.75) × 200회 = 360원

두 방법의 결과가 같습니다. 후보 나(4.4원)를 썼다면 880원입니다(추가 계산).

보충 · 실제 수업에서 더 넣을 것

실제로는 학습자가 같은 요청을 고쳐 다시 보내고, 대화가 길어지면 앞의 대화가 매번 입력에 다시 들어갑니다(1일차 p.79–81). 그래서 회당 입력 토큰이 처음보다 커지는 경우가 많습니다. 예산을 잡을 때는 횟수와 입력 길이에 여유를 두고, 실제 사용량은 수업 뒤 응답의 사용량 기록이나 콘솔에서 확인하세요.

42마지막 구간 · 총비용과 동시 사용 한도 [p.114]

총비용 (p.114)

20명 × 10회 = 200회. 얼마나 사용하는가.

동시 요청 조건

프로젝트 한도가 분당 10회라면, 20명이 한 번씩 동시에 시작할 때 제한될 수 있음. 한도의 적용 단위도 확인.

추가 계산 · 한도가 수업 시간에 미치는 영향 〔추가〕

text
동시 시작: 20명이 같은 1분 안에 요청 → 10회만 처리, 10회는 제한
전체 실습: 200회 ÷ 분당 10회 = 최소 20분 (요청이 고르게 나뉠 때)

비용은 360원에 불과해도, 이 한도라면 200회 실습에 최소 20분이 필요합니다. 학습자가 몰려서 요청하면 실패와 재시도가 겹쳐 더 길어집니다. 수업 설계에서는 비용보다 이 한도가 더 큰 제약이 될 수 있습니다. 시작 시각을 조 단위로 나누거나, 한 번에 하나만 요청하도록 안내하는 이유입니다.

오후 첫 구간 p.56의 원칙(“프로젝트별 한도라면 키를 나눠도 함께 계산한다”)이 여기서 쓰입니다. 학습자마다 키를 나눠 줘도 같은 프로젝트라면 한도는 하나입니다.

주의 · 알림은 멈추지 않는다 〔보충〕

비용 알림과 차단을 혼동하기 쉽습니다. 작성자가 알고 있는 Google Cloud의 예산 기능은, 예산을 넘으면 알림을 보낼 뿐 기본적으로 사용을 멈추지 않습니다. 실제로 멈추려면 별도의 차단 설정이나 자동화가 필요합니다. 다른 서비스도 비슷한 경우가 많으니, “알림을 설정했으니 예산을 넘지 않는다”고 안내하지 않도록 사용할 서비스의 문서를 확인하세요.

44마지막 구간 · 오류가 나면 먼저 확인할 곳 [p.116–117]

상황 (p.116) 첫 확인과 대응
한 사람만 접속 불가 그 계정의 접속·권한
모델 이용 권한 오류 키·접근 가능한 모델·권한
동시 요청 한도 제한 범위와 시작 시각 조정
제공자 장애 서비스 상태와 재시도 안내
표시 예 (p.117 · Gemini API) 먼저 확인할 내용 대응
403 PERMISSION_DENIED 키·프로젝트·모델의 접근 권한 권한과 설정을 확인
429 RESOURCE_EXHAUSTED 어떤 할당량·요청 한도인가 한도 확인 후 간격·사용량 조정
503 UNAVAILABLE 제공자 상태·일시 장애 안내 안내에 따라 대기·재시도

검증 〔공식 정의로 확인〕

세 코드와 이름의 짝은 Google의 공식 오류 코드 정의(googleapis 저장소의 google/rpc/code.proto)와 같습니다. 이 정의에서 PERMISSION_DENIED는 HTTP 403, RESOURCE_EXHAUSTED는 429, UNAVAILABLE은 503에 대응하고, 아래 보충의 INVALID_ARGUMENT(400), NOT_FOUND(404), INTERNAL(500), DEADLINE_EXCEEDED(504)도 같은 파일에서 확인했습니다. Gemini API가 이 코드 체계를 따른다는 것은 작성자 지식입니다. 자료의 단서 “같은 숫자라도 반환된 상세 메시지를 함께 읽는다”도 맞습니다. 예를 들어 429는 분당 요청 수 한도와 일일 한도 등 여러 원인에 같이 쓰입니다.

보충 · 수업에서 만날 수 있는 다른 코드

표시 예 흔한 원인 재시도로 해결되는가
400 INVALID_ARGUMENT 요청 형식·필드 이름·값이 잘못됨 (p.64 “요청 항목이 잘못됐다”) 아니요. 요청을 고친다
404 NOT_FOUND 모델 이름 오타, 없어졌거나 접근할 수 없는 모델 아니요. 모델 이름을 확인한다
500 INTERNAL 제공자 쪽 내부 오류. 입력이 지나치게 길 때도 나타날 수 있음 잠시 뒤 재시도, 반복되면 입력을 줄인다
504 DEADLINE_EXCEEDED 처리 시간이 제한을 넘음 입력이나 요청량을 줄여 재시도

목록의 코드와 이름은 위의 공식 정의로 확인했습니다. 서비스에서 나타나는 구체적인 원인은 공식 오류 안내에서 확인하세요. 오후 첫 구간 05절의 원칙대로, 권한·형식 오류는 기다려도 풀리지 않고 한도·장애는 간격을 두고 재시도합니다.

47마지막 구간 · 마무리 질문 · 자료는 내부에만 남는가 [p.123]

자료 p.123

조직 안에서 모델을 실행해도 외부 검색 도구를 쓴다면, “자료가 모두 내부에만 남는다”고 안내할 수 있을까?

먼저 답해 본 뒤 펼치기

안내할 수 없습니다. 모델은 조직 안에서 계산되더라도, 검색 도구에는 검색어가 전달됩니다. 검색어는 보통 질문이나 자료의 일부로 만들어지므로, 내부 자료의 내용이 외부 검색 서비스로 나갈 수 있습니다. 오후 둘째 구간 p.99의 “내부 모델도 외부 검색 도구를 연결하면 정보를 밖으로 보낼 수 있다”가 근거입니다.

정확한 안내는 이렇게 씁니다. “모델은 조직 내부에서 실행됩니다. 단, 검색 기능을 쓰면 검색어가 외부 검색 서비스로 전송됩니다. 내부 자료는 검색 기능을 끈 상태에서만 사용하세요.”

p.123은 다음 시간을 이렇게 예고합니다. “다음에는 모델이 자료에서 배우는 과정과 처음 보는 자료에서 성능을 확인하는 방법을 배운다.”

48핵심 정리

오전

  • 모델을 쓰려면 가중치 + 실행 프로그램 + 컴퓨터가 필요하고, 내려받기와 실행은 다른 일입니다.
  • 공개 여부, 실행 주체, 이용 통로, 허용 용도는 서로 다른 질문입니다. 같은 계열 모델도 라이선스가 다를 수 있습니다.
  • 저장량은 수치 개수 × 값 하나의 바이트 수로 어림할 수 있고, 실제 메모리는 입력 길이에 따라 더 늘어납니다.
  • 모델 카드는 개별 판본의 값을 읽고, 벤치마크 점수는 과제·설정·판본과 함께 읽습니다.
  • 모델의 제안과 설명은 실행의 증거가 아닙니다. 실행은 도구 기록으로 확인합니다.
  • 내 PC에서 돌릴 때는 모델 파일 크기 + 여유 메모리부터 확인하고, 속도는 메모리 대역폭이 좌우합니다.
  • 공개 점수와 점선(가격–지능)은 후보를 좁히는 용도이고, 최종 선택은 내 과제에서 직접 써 본 결과로 합니다.

오후 첫 구간

  • API 요청에는 모델·입력·생성 설정·주소·인증이 담기고, 응답에는 문장·종료 이유·사용량이 돌아옵니다.
  • 출력 한도는 상한이고, 비용은 실제 사용량 × 단가로 계산합니다.
  • 스트리밍은 첫 응답 시간을 줄일 뿐 완료 시간은 그대로입니다.
  • 요청 실패와 답변 내용의 오류는 확인할 곳이 다릅니다.
  • 후보 비교는 필요한 도움을 먼저 정하고, 같은 원자료로 시험하며, 모르는 값은 “확인할 수 없음”으로 남깁니다.
  • 요청 한도와 장애는 서비스가 직접 처리해야 하고, 오류가 나면 내 요청(400)·권한(403)·한도(429)·상태 페이지 순서로 확인합니다.
  • 사고 토큰은 출력 한도에 포함되므로 최대 토큰과 사고 수준을 함께 정합니다.
  • 프롬프트 캐시는 같은 앞부분의 처리를 저장하는 기능이며, 대화를 다시 보내는 것과는 다릅니다.
  • 검색은 따로 과금되고 서비스마다 엔진이 다릅니다. API 스펙을 보면 구현 가능 여부가 바로 보입니다.

오후 둘째 구간

  • 프롬프팅과 RAG는 입력을 바꾸고, 미세조정은 모델을 바꿉니다.
  • RAG의 답이 틀리면 검색 결과부터 확인합니다.
  • 바뀌는 사실은 입력으로, 반복 행동은 예시나 추가 학습으로 다룹니다. 세 방법은 순서가 아니라 필요에 따른 선택입니다.
  • 실행 장소·접근 권한·연결된 도구는 서로 다른 조건입니다.
  • 약관은 학습 이용과 기록 보존을 따로 읽고, 내 요금제와 지역에 적용되는 조항인지 확인합니다.

마지막 구간
