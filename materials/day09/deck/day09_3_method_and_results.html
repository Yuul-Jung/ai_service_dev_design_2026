자료 p.77–79 · 스킬

스킬은 작업 절차와 자료를 묶는다: 반복해서 설명하던 작업 방법을 파일에 정리해 필요할 때 불러온다. 스킬의 설명에는 언제 쓸지, 본문에는 어떻게 할지를 적고, 참고 자료와 보조 프로그램도 함께 둘 수 있다. “실제 작업에는 읽기·쓰기 같은 실행 도구가 필요하다.” 공개 프레젠테이션 스킬의 구성: pptx 폴더 → SKILL.md(작업 설명과 절차), scripts 폴더(보조 프로그램) → thumbnail.py(슬라이드를 모아 보는 프로그램). 모델은 절차 파일을 읽고 필요하면 실행 도구로 보조 프로그램을 사용한다. name · description(스킬의 이름과 적용할 작업), SKILL.md 본문(읽기·수정·제작에 따라 작업 방법 안내), scripts/thumbnail.py(슬라이드 축소 모음 이미지를 만드는 프로그램), 검수 안내(만든 자료를 열어 내용과 화면 확인).

검증 · 공개 pptx 스킬의 실제 구조 p.78–79 일치

Anthropic의 공개 스킬 저장소(anthropics/skills)에서 pptx 스킬을 확인했습니다. 폴더에는 SKILL.md와 scripts 폴더(thumbnail.py·add_slide.py·clean.py 등)가 있고, SKILL.md의 머리말(frontmatter)에 name: pptx와 긴 description(‘.pptx 파일이 어떤 식으로든 관련될 때 이 스킬을 쓴다’로 시작해 읽기·만들기 등 적용할 작업을 열거)이 있습니다. 본문은 파일을 읽을 때는 markitdown, 슬라이드 격자 이미지를 만들 때는 python scripts/thumbnail.py deck.pptx를 쓰라고 안내합니다. thumbnail.py의 머리말 설명은 “슬라이드 축소 이미지의 격자를 만든다, 각 축소 이미지에 XML 파일 이름(slide1.xml)을 붙인다”입니다. 슬라이드의 ‘이름·적용 조건(description) → 본문 절차 → 보조 프로그램’ 구분과 같고, 스킬 본문은 ‘읽는’ 것이지 ‘실행’되는 것이 아니며 프로그램(scripts)은 실행 도구가 돌려야 한다는 p.82의 구분도 이 구조에서 나옵니다. 저장소 변경 이력 때문에 파일 목록과 문구는 시점에 따라 바뀔 수 있습니다.

자료 p.80–82 · 스킬을 읽고 쓰는 과정

스킬 본문에는 실제 작업 순서와 기준이 있다(기존 덱 읽기 → 구조·내용 수정 → 결과 열어 확인: 본문과 화면을 읽고 수정할 내용에 맞는 슬라이드를 고르고, 슬라이드를 추가·배치한 뒤 텍스트와 그림을 고치고, 본문의 누락·순서와 화면의 겹침·잘림을 찾아 수정). AI는 스킬을 고른 뒤 본문과 참조 자료를 읽는다(스킬 선택: 모델이 설명을 보고 현재 작업에 쓸 스킬을 고름 → 본문 읽기: 호출한 스킬의 절차와 기준을 모델 입력에 넣음 → 참조 파일 읽기: 본문이 가리킨 자료를 필요한 작업에서 추가로 읽음. 클로드 코드의 일반 세션 기본 동작이며 사용자도 스킬을 지정해 호출할 수 있다). 스킬 읽기와 프로그램 실행을 구별한다(슬라이드 축소 모음 생성 안내: 모델이 안내를 읽고 대상 덱과 프로그램을 정함 / 보조 프로그램 실행: 실행 도구가 프로그램을 돌려 이미지를 만들고 모델은 그 이미지를 열어 배치를 확인).

확인 불가 · 스킬이 모델 입력에 들어가는 방식과 순서 제품 동작 미확인

‘설명만 먼저 보여 주고 필요할 때 본문을 불러온다’는 단계적 읽기(p.81)는 Claude Code의 공식 문서에 접속할 수 없어 제품이 실제로 그렇게 동작하는지는 확인하지 못했습니다. 저장소의 스킬 구조(머리말의 이름·설명, 본문, 부속 파일)는 이 설계와 맞지만, 호출 시점과 기본 동작은 제품과 버전에 따라 다를 수 있습니다(슬라이드도 ‘일반 세션 기본 동작’으로 한정). 다만 7일차 p.118의 ‘정보가 필요한 시점에 맞춰 입력을 구성한다’와 같은 원리이며, 설명(description)이 구체적이어야 모델이 올바른 스킬을 고른다는 점은 pptx 스킬의 긴 적용 조건 설명이 보여 줍니다.

자료 p.83–86 · 반복할 방법 찾기

앞서 만든 설명 파일(정의 뒤에 원문 링크, 종류·관계·기능을 연결한 설명, 원문과 해석을 구별한 문단)에서 다음 작업에도 필요한 방법을 찾는다. AI와 결과를 다듬은 뒤 그 결과에 필요했던 절차와 기준을 정리한다. 작업 방법을 스킬의 설명과 본문에 담는다(언제 사용하는가: 자료를 읽어 근거 있는 설명 파일을 만들 때 / 먼저 확인할 입력: 설명할 질문·자료 위치·결과 저장 위치 / 본문의 작업 절차: 원문 읽기 → 설명과 근거 작성 → 파일 저장 / 결과를 볼 기준: 질문에 답하는가? 근거가 맞고 해석과 구별되는가? / 참조할 예시와 필요한 읽기·쓰기 기능). 계속 적용할 원칙은 지침에, 작업별 절차와 자료는 스킬에 둔다(기존 지침으로 충분한지 먼저 살피고, 반복 작업이 길어지면 절차와 참고 자료를 묶고, 필요한 실행 기능은 별도로 갖춘다). 질문이 바뀌면 읽을 자료와 설명도 달라진다(원문 20쪽에서 데이터가 생기는 곳을 세 종류로 설명하기).

7일차 p.88–98의 ‘피드백 속의 반복할 기준을 지시로 옮기기’를 스킬이라는 형식으로 묶는 단계입니다. 구분 기준은 간단합니다. 모든 작업에 적용되는 원칙(‘확인한 것과 못한 것을 구별해 보고한다’)은 지침(7일차 p.70)에, 특정 작업의 절차·참고 자료(‘원문 읽기 → 근거와 함께 설명 → 저장’)는 스킬에 둡니다. 슬라이드의 순서도 같습니다. 먼저 기존 지침으로 충분한지 살피고, 반복 작업이 길어질 때만 스킬로 묶습니다.

검증 · n8n 일정 트리거의 공식 설명과 시간대의 영향 (공식 문서·직접 계산) p.88 일치 추가 계산 서버 시간대 기본값은 미확인

같은 ‘오전 9시 15분’이 시간대에 따라 가리키는 UTC 시각 (2026-11-16) Asia/Seoul 09:15 → UTC 00:15 UTC 09:15 → UTC 09:15 America/New_York 09:15 → UTC 14:15 이틀마다(Asia/Seoul 09:15): 11/16 · 11/18 · 11/20 · 11/22

같은 ‘9시 15분’이어도 시간대가 다르면 실제 실행 시각이 크게 달라집니다(위 예에서 서울과 뉴욕은 14시간 차이, 서울과 UTC는 9시간 차이). “워크플로에 시간대가 없으면 서버의 시간대를 쓴다”(슬라이드)는 문장은 n8n 문서의 해당 쪽에서 찾지 못해 확인하지 못했습니다. 그러므로 서버가 다른 나라에 있을 수 있는 서비스는 시간대를 워크플로에 명시하는 편이 안전합니다.

자료 p.89–91 · 웹훅

웹훅은 외부 요청을 받아 작업을 시작한다(외부 서비스 → 웹훅 주소 → 워크플로 실행: 받은 데이터를 입력으로 전달). 요청을 보낼 주소·방식과 받는 쪽의 인증 조건을 맞춘다. 웹훅으로 결제 결과를 앱에 전달할 수 있다(결제 서비스가 결제 상태가 바뀌면 해당 결제의 정보와 상태를 전송 → 앱의 수신 주소가 웹훅 요청을 받고 전달된 결제 정보를 확인 → 앱의 후속 처리가 그 결제에 해당하는 사용자를 찾아 이용 상태를 바꿈). “웹훅은 사건의 데이터를 전달한다. 받은 뒤 무엇을 할지는 앱에서 구성한다.” n8n 웹훅: 테스트 주소(테스트 수신을 시작하고 요청을 보내 확인, 받은 데이터를 편집 화면에서 살핌), 운영 주소(워크플로를 게시해 실제 요청을 받음, 처리한 데이터는 실행 기록에서 살핌).

검증 · n8n 웹훅의 테스트·운영 주소와 인증 (공식 문서)와 받은 요청의 진위 확인 (직접 실행) p.91 일치 추가 실행

n8n 공식 문서는 “테스트용과 운영용 웹훅 주소가 다르다. 테스트 주소는 ‘테스트 이벤트 수신’을 선택하면 받은 데이터를 편집기에 보여 주고, 운영 주소는 워크플로를 게시할 때 등록되며 데이터를 편집기에 보여 주지 않고 실행 기록에서 볼 수 있다”고 설명합니다. 또 웹훅을 부르는 서비스에 인증을 요구할 수 있으며 Basic·Header·JWT 인증 등을 지원한다고 밝혀 ‘받는 쪽의 인증 조건을 맞춘다’와 같습니다.

공유한 비밀값으로 요청 본문의 서명(HMAC-SHA256)을 계산해 비교 원본 본문 {"payment":"paid","user":42} → 서명 일치: True 본문을 바꾼 요청 {"payment":"paid","user":43} → 서명 일치: False

웹훅 주소는 누구나 보낼 수 있는 주소이므로 받은 데이터가 진짜 결제 서비스에서 온 것인지 확인하지 않으면 위조된 ‘결제 완료’로 유료 기능이 열릴 수 있습니다. 위 서명 확인은 그 방법의 하나입니다(결제 서비스마다 서명 방식이 달라 각 서비스의 안내를 따라야 하고, 위 계산은 방식의 원리만 보인 작성자 실행입니다). p.90의 ‘전달된 결제 정보를 확인한다’ 단계가 바로 이 확인입니다.

후크는 실행 중 특정 사건에 처리를 연결한다. 도구가 성공하면 사용자의 일도 끝난 걸까? 어느 프로그램이 무엇을 바꿨는가? 한 도구가 돌려준 내용은 그 도구가 맡은 처리의 결과다. 실제 파일·서비스가 원하는 상태로 바뀌었는지 확인한다. 결제 완료와 유료 기능 이용은 다른 처리다(결제 서비스의 결제 처리 결과 → 결과 전달 → 내 앱의 사용자의 이용 상태 변경). “결제가 완료됐다는 정보만으로 앱의 처리 결과까지 알 수는 없다.” 요청과 결과를 같은 작업에 연결해 읽는다(요청: 어느 파일에 어떤 내용을 저장하라고 보냈는가? 반환: 쓰기 도구가 성공·오류 중 무엇을 돌려줬는가? 실제 상태: 지정한 위치에 파일이 있고 내용이 맞는가? 다음 확인: 실행 기록과 저장된 파일 중 무엇을 더 읽어야 하는가?).

처리가 끝나도 응답을 늦게 받을 수 있다(앱이 외부 문서에 저장을 요청하고 응답을 기다림 → 서비스는 문서 저장을 끝냈지만 응답은 아직 도착하지 않음 → 앱은 대기 시간이 지나 시간초과로 표시). “시간초과는 응답을 기다리다 멈춘 상태다. 실제 저장 결과를 별도로 확인한다.” 시간초과가 나도 외부 작업은 끝났을 수 있다. 변경 대상과 서비스 기록에서 처리 여부를 먼저 알아보고, 같은 작업을 반복할지는 확인 결과에 따라 정한다.

검증 · 시간초과 뒤에도 외부 작업이 끝나는 경우 (직접 실행) p.101–102 확인 추가 실행

‘응답 없음’과 ‘처리 안 됨’은 다릅니다. 같은 요청을 다시 보내기 전에 대상이 이미 바뀌었는지(파일·서비스 기록)를 먼저 확인해야 하고, 같은 요청을 여러 번 보내도 결과가 한 번과 같도록 설계(‘같은 요청을 반복해도 결과가 같게 만드는 것’)하면 재시도가 안전합니다(작성자 조언). 위 실험은 시간초과를 단순화해 흉내 낸 것이며 실제 서비스의 응답 지연 양상은 다릅니다.

자료 속 작업 지시는 언제 실행할까? 스킬의 내용을 설명해 달라면 “기존 덱을 읽고 수정한다”는 문장을 설명할 대상으로 읽는다. 그 스킬로 덱을 고쳐 달라면 사용자가 수정할 덱과 요청 범위를 지정하고, 스킬의 절차를 참고해 허용한 작업을 수행한다(스킬 안의 문장이 실제 덱을 수정하라는 요청은 아니다). 프롬프트 인젝션: 자료 속 지시가 작업을 바꾼다. 도구가 돌려준 내용은 다시 모델 입력에 들어간다(사용자의 요청·허용 범위 = 해야 할 일과 허용한 행동 / 외부 문서·도구의 반환 = 그 일을 수행할 때 참고할 자료). 모델이 자료 속 지시를 사용자 명령처럼 따르면 원래 작업이 바뀔 수 있다. 자료를 읽을 때도 실행 권한을 제한해야 한다(내용을 읽는 단계: 출처와 인용 범위를 구별, 외부 내용은 작업 자료로 읽도록 지침 / 실행하는 단계: 필요한 도구·대상만 허용, 민감한 변경은 확인 절차와 실제 접근 제한).

OWASP의 대규모 언어 모델 위험 목록(LLM01 프롬프트 주입)은 이 위험을 “모델이 프롬프트 데이터를 처리하는 방식에서 생기며, 지침을 위반하거나 무단 접근을 가능하게 하거나 중요한 결정에 영향을 줄 수 있다”고 설명하고, 모델의 확률적 성격 때문에 완벽한 예방법이 있는지 불분명하며 영향을 줄이는 완화책(외부 콘텐츠의 분리·식별 등)을 제시한다고 7일차에서 확인했습니다. 이 쪽의 ‘내용을 읽는 단계의 지침’은 그 완화책에 해당하고, ‘실행하는 단계의 허용 제한’은 지침이 뚫려도 피해를 제한하는 방어층입니다.

오전에 직접 실행한 허용 폴더 검사가 바로 그 두 번째 층의 예입니다. 모델이 자료 속 지시에 속아 비공개/비밀.txt 읽기를 요청해도 프로그램이 접근을 막았습니다. 그래서 자료를 읽는 도구에는 쓰기·삭제·외부 전송 같은 도구를 함께 주지 않거나, 주더라도 민감한 변경은 사람의 승인을 거치게 하는 것이 안전합니다(작성자 조언). 외부 문서·웹 자료·메일처럼 통제하지 못하는 출처가 도구 반환으로 모델 입력에 들어오는 구성일수록 이 위험이 커집니다.

내 작업에 필요한 방법을 AI와 다듬는다. 원하는 결과를 구체화하고 그 결과를 만드는 절차와 기능을 정한다. 내 자료로 결과를 다듬으며 필요한 설명과 기술을 더 공부한다. 반복할 일이 있다면 방법을 정리해 다른 요청에도 적용해 본다. 실행 환경이 없다면 준비할 기능과 설정까지 구체적으로 설명한다.

06핵심 정리

  • 도구는 무엇을 할 수 있는가, 지침·스킬은 어떻게 일하는가입니다. 스킬(이름·설명 / 본문 절차 / 보조 프로그램)은 읽는 것이고 프로그램은 실행 도구가 돌립니다. 모든 작업의 원칙은 지침, 작업별 절차는 스킬에 둡니다.
  • 작업은 사람·일정·웹훅·후크로 시작합니다. 같은 09:15도 시간대에 따라 실제 시각이 달라지고(서울 = UTC 00:15), 웹훅은 진위 확인이 필요하며, ‘매번 해야 하는 일’은 후크로 확정합니다.
  • 도구의 성공은 그 도구의 처리 결과일 뿐이므로 요청·반환·실제 상태를 따로 확인합니다.
  • 오류는 프로토콜 오류(-32602)와 도구 실행 오류(isError: true)로 나뉘고, 후자는 모델이 고쳐 재시도할 수 있게 제공합니다. 시간초과 뒤에도 작업은 끝났을 수 있습니다.
  • 자료 속 지시는 자료이지 명령이 아닙니다. 경계를 드러내는 것은 완화책이므로 읽는 도구에 쓰기·삭제 같은 실행 권한을 함께 주지 않거나 제한합니다.
