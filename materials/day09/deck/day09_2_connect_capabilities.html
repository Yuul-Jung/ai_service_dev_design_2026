MCPModel Context Protocol

호스트(AI 앱)·클라이언트·서버 구조로 도구(모델 제어)·자료(앱 제어)·지시 양식(사용자 제어)을 제공하는 공통 규약입니다. 서버는 로컬(stdio)이나 원격(HTTP)입니다(p.54–58).

인증과 권한Authentication vs. authorization

인증은 신원 확인, 권한은 허용한 범위입니다. 허용은 외부 서비스·AI 앱·실행 환경의 세 층에서 따로 정하며 접근 토큰은 언어 모델의 토큰과 다릅니다(p.60–63).

등록·접속·호출·작업 완료는 다른 상태이고, 허용은 세 층에서 따로 정하며, 도구가 많으면 필요한 정의만 불러옵니다.

02MCP · 기능을 소개하고 이용하는 공통 규약p.53–59

자료 p.53–54

외부 기능마다 연결 방식을 새로 만들까? 기능별 연결을 직접 만들면 각 기능의 사용법에 맞춰 요청·결과 처리를 연결하고 앱을 바꾸면 그 연결도 다시 살핀다. 공통 규약을 지원하면 앱과 기능 제공 프로그램이 같은 약속으로 통신하며 MCP가 그 약속을 정한다. MCP는 서로 다른 기능을 공통된 요청·응답 방식으로 연결한다. AI 앱은 같은 형식으로 기능 목록과 입력 규칙을 읽고, 서버는 요청을 실제 기능에 연결하고 결과를 돌려주며, 지원하는 AI 앱에서는 같은 서버 연결을 재사용할 수 있다.

검증 · MCP의 구조와 제공 요소를 공식 사양으로 확인 p.55·p.58 일치

  • 역할: MCP 공식 사양(modelcontextprotocol 저장소의 문서)의 구조 설명은 “클라이언트–호스트–서버 구조”이며 하나의 호스트가 여러 클라이언트 인스턴스를 실행한다고 밝힙니다. 슬라이드의 ‘호스트: 사용자가 쓰는 AI 앱 / 클라이언트: 서버와 통신하는 부분 / 서버: 기능·자료를 제공하는 프로그램’과 같습니다.
  • 제공 요소: 서버가 제공하는 것은 Prompts(미리 정한 지시 틀) · Resources(모델에 맥락이 되는 구조화된 자료) · Tools(모델이 동작을 수행하게 하는 실행 기능)의 세 가지입니다. 슬라이드의 ‘지시 양식 · 자료 · 도구’(p.58)와 같고, 사양은 누가 제어하는지도 구분합니다(지시 틀은 사용자 제어, 자료는 앱 제어, 도구는 모델이 호출).
  • 전송 방식: 사양은 stdio(표준 입출력)와 Streamable HTTP의 두 전송 방식을 정의합니다. 슬라이드의 ‘로컬 서버(내 컴퓨터에서 프로그램 실행: 실행 명령과 필요한 파일·환경) / 원격 서버(네트워크의 서버에 접속: 주소와 인증정보)’(p.56)와 대응합니다.

사양 저장소에는 여러 날짜의 사양 버전(2024-11-05부터 2025-11-25, 그 뒤 버전과 초안까지)이 있어 세부(예: 상태 유지 여부, 전송 방식의 이름)가 버전에 따라 달라질 수 있으므로 쓰는 앱이 어느 버전을 지원하는지 확인해야 합니다. 슬라이드의 세 요소와 두 연결 방식은 이 버전들에서 공통입니다.

자료 p.57 · p.59

MCP 서버가 기존 서비스의 API를 쓸 수도 있다(AI 앱 → MCP 서버 → 업무 서비스 API: 서버가 받은 요청을 서비스 API에 맞게 전달하고 결과를 돌려준다). 같은 문서도 무엇을 제공하느냐가 다르다. 도구(문서를 검색하는 기능: 검색어를 보내면 찾아낸 문서 목록을 받는다), 자료(서버가 참조용으로 제공하는 문서 내용: 주소로 지정한 자료를 앱이 읽어 활용), 지시 양식(문서 설명에 쓸 지시 틀: 대상·문서를 넣으면 설명 요청을 구성). 기능을 실행하는 것, 내용을 제공하는 것, 요청을 구성하는 것을 구별한다.

같은 ‘문서’라도 도구(검색을 실행)와 자료(내용을 주소로 제공)와 지시 양식(요청의 틀)로 제공할 수 있다는 것이 p.59의 요점입니다. 도구는 입력을 받아 처리하고 결과를 돌려주지만, 자료는 지정한 주소의 내용을 앱이 읽어 가고, 지시 양식은 입력 값을 넣어 요청을 만들어 줍니다. 앞의 사양이 이 세 가지를 서로 다른 제어 주체로 구분하는 이유입니다.

자료 p.62–64

접근 권한과 실행 허용은 서로 다른 곳에서 정한다. 외부 서비스(어느 계정이 어떤 자료·기능을 쓸 수 있는가), AI 앱(어떤 도구를 허용하고 언제 승인을 받는가), 실행 환경(어떤 파일·네트워크에 접근할 수 있는가). 앱에서 허용해도 서비스 권한이 필요하다(앱에서 도구 실행을 허용했지만 연결 계정은 읽기만 가능하면 저장 요청은 거절될 수 있다). 서버 등록 뒤 연결·인증 상태를 확인한다(등록 → 필요한 인증·권한 → 기능 이용). “등록, 접속, 호출, 작업 완료는 서로 다른 상태다.”

검증 · 세 층의 허용은 따로 있고, 하나라도 막히면 실패한다 (앞의 실행 구성으로 확인) p.62–63 논리 확인 제품별 설정은 미확인

앞의 직접 실행에서 읽기·쓰기 도구는 도구 등록(앱의 허용)과 폴더 허용(실행 환경의 접근 제한)을 모두 통과해야 처리됐고, 등록하지 않은 delete_file은 앱 단계에서, 허용 밖 폴더 읽기는 실행 환경 단계에서 각각 막혔습니다. 같은 이유로 외부 서비스의 계정 권한이 읽기 전용이면 앱이 호출을 허용하고 실행 환경이 통과시켜도 서비스가 쓰기를 거절합니다. 그래서 오류가 나면 ‘어느 층에서 막혔는지’를 먼저 나눕니다(오후 2의 03절). MCP 사양 저장소에는 연결의 권한 부여(authorization) 문서가 별도로 있어 ‘인증이 필요한 서버’의 존재(p.64)가 사양의 일부임을 확인했고, 각 서비스의 계정·권한 설정 화면은 제품 안내를 따라야 합니다.

주의 · API 키와 접근 토큰은 비밀이다 (7일차 연결)

접근 자격을 증명하는 정보는 외부에 노출되면 그대로 도용됩니다. 7일차 p.58·오후 첫 02절에서 본 것처럼 브라우저로 전달되는 값은 사용자가 볼 수 있으므로 서버 쪽 설정에 두고, 수업 자료·화면 공유·저장소에는 실제 값 대신 가짜 값을 씁니다.

04실제 연결 예 · 로컬 QMD 등록과 원격 Sentry 연결p.65–68

자료 p.65–66 · 로컬 검색 기능 등록

Claude Desktop의 연결 설정에 QMD 검색 프로그램을 등록하는 공식 예: 연결 이름 qmd(앱에서 이 연결을 구별할 이름), 실행할 프로그램 command: qmd, 프로그램 실행 옵션 args: ["mcp"](MCP 서버 기능으로 실행). 연결 전에 준비할 것: QMD 설치·검색할 폴더 등록·검색용 색인 준비. 검색 결과를 읽고 필요한 본문을 가져온다: query(검색어를 보내 관련 문서 후보와 위치·식별자를 받음) → get(문서 위치나 식별자를 보내면 해당 문서의 본문을 받음) → 모델이 근거로 설명하고 쓰기 도구가 파일을 저장한다.

검증 · QMD의 MCP 설정을 공식 저장소로 확인 일치

QMD의 공식 저장소 README는 이 도구가 “명령줄에서도 잘 작동하지만 더 긴밀한 통합을 위해 MCP 서버도 제공한다”고 하며 MCP 설정 예에 "mcpServers" 아래 "command": "qmd", "args": ["mcp"]를 보여 줍니다. 슬라이드의 연결 이름·실행 프로그램·옵션과 같고, README는 Claude Code의 설정 파일에도 같은 형식으로 쓸 수 있음을 보여 줍니다. 8일차에서 확인한 qmd query·qmd get이 MCP에서는 검색·본문 읽기 기능으로 제공됩니다.

자료 p.67–68 · 원격 연결

Claude Code에서 Sentry 오류 정보를 읽는 공식 예: 연결할 서비스 Sentry(오류·문제 정보를 다루는 서비스), 서버 별칭 sentry, 연결 방식 http(원격 주소에 접속), 서버 주소 https://mcp.sentry.dev/mcp. “주소 등록만으로 계정 인증이 끝나는 것은 아니다.” 등록 뒤에는 연결 상태와 기능을 읽는다: /mcp(대화창의 명령으로 서버·연결 상태 확인), 계정 인증(필요한 서버는 로그인해 접근 허용), 제공 기능(이번 연결에서 사용할 도구와 입력), 실행 기록(어떤 기능을 호출했고 무엇이 돌아왔는지). 등록된 이름만으로 접속·호출 성공을 알 수는 없다.

검증 · Claude Code의 연결 명령 명령 존재 확인 Sentry 서버 주소·옵션은 미확인

Claude Code의 공식 변경 기록에는 claude mcp add(서버 등록과 제거)와 /mcp(서버의 연결 상태 확인, 인증이 필요한 서버의 ‘다시 연결’ 등) 명령이 여러 번 나와 슬라이드가 말한 명령의 존재는 확인됩니다. 특히 변경 기록은 인증이 만료된 서버를 /mcp가 ‘연결됨’으로 잘못 보여 주던 오류를 고친 항목이 있어, 슬라이드의 “등록된 이름만으로 접속·호출 성공을 알 수는 없다”가 실제로 일어나는 문제임을 보여 줍니다. Sentry의 서버 주소(https://mcp.sentry.dev/mcp)와 --transport http 옵션은 Sentry·Claude Code의 공식 안내에 접속할 수 없어 확인하지 못했습니다(슬라이드가 ‘공식 예’로 제시).

05도구가 많으면 필요한 정의만 불러온다 · 도구 탐색과 지연 로딩p.69–71

자료 p.69–71

등록한 도구의 설명을 전부 읽혀야 할까? 모든 정의를 처음부터 전달하면 기능 이름과 입력 규칙도 모델 입력의 일부라서 도구를 많이 연결할수록 사용법 설명도 길어지고, 필요한 정의를 찾아 전달하면 필요한 기능을 먼저 찾고 그 사용법을 불러온 뒤 입력 값을 채워 호출한다. 도구 탐색(이름·설명 등에서 필요한 기능을 찾음) → 정의 불러오기(선택한 기능의 입력 형식을 읽음) → 도구 호출(실제 입력 값을 보내 실행). 필요할 때 정의를 모델 입력에 불러오는 방식: 지연 로딩. 공식 예: 등록된 정의 get_weather·search_files, 처음 모델 입력은 탐색 도구와 바로 제공할 정의, 탐색 결과는 get_weather를 가리키는 참조. “탐색은 기능을 찾는 일, 호출은 그 기능을 실행하는 일이다.”

검증 · 도구 정의를 전부 넣으면 입력이 얼마나 길어지는가 (직접 계산)와 SDK의 도구 탐색 기능 p.69 확인 추가 계산 토큰은 근사치

가상의 도구 정의 50개(이름·설명·입력 스키마)를 JSON으로 만들어 토큰 수를 계산 (o200k_base 기준 근사) 50개를 모두 전달: 약 4,602토큰 필요한 3개만 전달: 약 278토큰 → 약 16.6배 짧음 이름만 전달(탐색용): 약 303토큰

도구가 많을수록 사용법 설명이 매 요청의 입력을 차지합니다(위 가상 정의 50개는 약 4,600토큰). 필요한 정의만 불러오면 입력이 크게 줄어듭니다. Anthropic Python SDK의 소스에는 도구 탐색 도구(tool_search_tool_regex·tool_search_tool_bm25의 2025-11-19판)와 정의를 나중에 불러오게 하는 defer_loading 옵션이 있어 슬라이드의 ‘도구 탐색·지연 로딩’이 실제 기능임을 확인했습니다. 정의 50개의 크기는 작성자가 만든 가상 값이며 토큰 수는 모델마다 다릅니다.

주의 · 탐색이 틀리면 필요한 도구를 못 찾는다

지연 로딩은 입력을 줄이는 대신 탐색 단계에서 필요한 도구를 놓칠 위험을 만듭니다. 도구의 이름과 설명이 모호하면 탐색이 어긋나므로, 이름·설명을 구체적으로 쓰고 자주 쓰는 소수의 도구는 처음부터 제공하는 구성(p.71의 ‘바로 제공할 정의’)이 흔합니다.

07핵심 정리

  • 필요한 기능은 내장 · API/MCP · 작업공간 · 브라우저 중에서 가져오며, 위치를 아는 자료는 파일 읽기로, 위치를 찾아야 하면 검색 도구로 충분합니다.
  • MCP는 호스트(AI 앱) – 클라이언트 – 서버 구조로 도구·자료·지시 양식을 제공하는 공통 규약이며, 서버는 로컬(stdio)이나 원격(HTTP)일 수 있습니다. 버전에 따라 세부가 다릅니다.
  • 인증(누구인가)과 권한(무엇을 허용하는가)은 다르고, 허용은 외부 서비스·AI 앱·실행 환경의 세 층에서 따로 정해 하나라도 막히면 실패합니다. 접근 토큰은 언어 모델의 토큰과 다릅니다.
  • 등록·접속·호출·작업 완료는 서로 다른 상태이므로 /mcp 등으로 연결 상태와 제공 기능을 읽어 확인합니다.
  • 도구가 많으면 정의 전체를 넣지 않고 필요한 정의만 불러옵니다(가상 50개 약 4,602토큰 대 3개 278토큰). 대신 탐색이 틀리면 도구를 놓칠 수 있습니다.
