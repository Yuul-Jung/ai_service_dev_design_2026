“다음에 뭘 만들지”보다 “무엇이 문제인지”를 먼저 찾는다(처음 해결하려던 일은 무엇이었나? 실제 사용자는 어디에서 도움을 얻거나 막히나? 다른 기술이나 더 간단한 방식으로 나아질 수 있나?). 실제 사용과 다른 해결법에서 개선의 근거를 찾는다(내 서비스를 쓰는 사람: 쓰는 과정을 보고 막히는 곳과 이유를 듣고 피드백 폼·연락 경로를 마련 / 비슷한 문제의 다른 해결법: 실제 리뷰·사례에서 방법을 찾고 AI와 기술·현재 구조를 살피며 다른 해결 가능성을 공부). “다른 제품의 리뷰와 AI의 추측은 내 서비스 사용자의 반응과 구별한다.” 사용 중 겪는 어려움에 따라 개선할 곳이 달라진다(진행 상황을 모름 → 상태·오류 안내 / 첫 응답까지 오래 걸림 → 모델·입력·앞단 처리의 시간을 비교 / 답이 일을 돕지 못함 → 질문·근거 자료·출력 내용과 사용 목적을 비교). 무엇을 개선하려는지에 따라 읽을 자료가 달라진다(원하는 일을 해냈는가: 사용 목적·실제 결과·이용자의 의견 / 어디에서 오래 걸렸는가: 시작·종료와 처리별 실행 기록 / 바꾼 것이 도움이 됐는가: 변경 조건과 이전·이후 결과 / 다른 방법은 없는가: 다른 해결 사례·최신 기술·현재 서비스 구조).

7일차 오전의 ‘기능을 정했다고 목적이 정해진 것은 아니다’(p.6)와 ‘배달 앱 대신 맛있던 가게를 다시 찾기’(p.11–12)가 서비스를 쓰는 단계에서 되풀이됩니다. 기능을 더하는 것보다 ‘어디서 막히는가’를 먼저 찾으면, 앞 절의 대기 안내처럼 작은 변경(진행 상황을 알림)이 같은 문제를 더 싸게 풀 수 있습니다. 세 가지 어려움(모름·느림·도움이 안 됨)은 개선할 곳이 서로 다릅니다. 같은 ‘느리다’는 호소도 응답 시간을 줄이는 변경이 아니라 안내를 바꾸는 변경으로 풀릴 수 있습니다(앞 절의 사례가 ‘기다리는 이유를 알릴 뿐 응답을 빠르게 하지는 않는다’). 다만 이것이 사용자에게 도움이 됐는지는 실제 사용자의 반응으로 확인해야 하며, 다른 제품의 리뷰나 AI의 추측으로 대신할 수 없습니다(p.89).

02실행 기록 읽기 · 트레이스·세션·시간의 포함 관계p.92–94

자료 p.92–94 · Langfuse

한 요청 안에서 어떤 처리가 이어졌는지 본다(요청 한 번의 실행 기록 · 트레이스: 입력 처리 → 모델·도구 처리 → 응답 제공). 개별 처리의 기록을 ‘관측 기록’이라 부른다. 입출력·시간·오류를 같은 요청에 연결한다. 세션은 관련된 요청의 기록을 묶는 단위다(① 세션 ② 요청 목록 ③ 선택한 요청의 메시지·도구, Langfuse: 실행 기록·평가 도구 · 세션 → 요청 → 처리 기록 · 공식 화면). 요청 전체 시간에 하위 처리 시간이 포함된다(요청 전체 처리 3.1초 = 검색 0.4초 + 모델 호출 2.6초). “전체 처리와 그 안의 처리를 더하면 같은 시간을 두 번 셀 수 있다.” (공식 문서의 설명용 값 · 상자는 포함 관계이며 시간 축·길이 비율이 아니다.)

검증 · Langfuse의 성격과, 포함된 시간을 더하면 두 번 센다 (공식 README·직접 계산) p.92–94 일치 추가 계산 세션 화면은 미확인

Langfuse의 공식 README는 이 도구를 “에이전트 평가와 관측을 위한 오픈소스 AI 엔지니어링 플랫폼”이라 설명하며 기능으로 AI 관측(Observability: 추적 기록을 수집해 LLM 호출 등을 추적), 평가(Evaluations: LLM-as-a-judge·코드 기반 등), 프롬프트 관리 등을 듭니다. 또 OpenTelemetry 위에서 만들어져 어떤 언어·프레임워크에서도 추적 기록을 보낼 수 있다고 밝힙니다. 슬라이드의 ‘실행 기록·평가 도구’ 설명과 같습니다. ‘세션 → 요청 → 처리 기록’의 화면 구성은 공식 문서에 접속할 수 없어 확인하지 못했습니다.

요청 전체 처리 3.1초 ⊃ 검색 0.4초 + 모델 호출 2.6초 (슬라이드의 설명용 값) 하위 처리의 합 = 0.4 + 2.6 = 3.0초 (하위 밖의 시간 0.1초) 모든 처리를 단순히 더하면 = 3.1 + 0.4 + 2.6 = 6.1초 → 같은 시간을 두 번 센 값 (실제는 3.1초)

하위 처리의 합(3.0초)이 전체(3.1초)보다 0.1초 작은 것은 하위 처리 사이·앞뒤의 시간(요청 접수·응답 구성 등)이 기록되지 않은 부분일 수 있다는 뜻입니다(작성자 해석). 그래서 ‘어디에서 오래 걸렸는가’(p.91)를 볼 때는 전체와 하위 처리를 나란히 놓되 더하지 않고, 가장 긴 하위 처리(여기서는 모델 호출 2.6초)가 전체의 몇 %인지(약 84%)로 읽습니다. 슬라이드의 3.1초 등은 공식 문서의 설명용 값이며 실제 측정이 아닙니다.

04실험 추적·운영 기록·자동 평가·LLMOps · 변경 조건과 결과를 함께 보관한다p.100–103

실험 추적은 변경 조건과 결과를 함께 보관한다(같은 질문의 답이 바뀌었다면 입력·모델·지침·도구·코드도 함께 본다: 평가셋과 기준을 정하고 조건을 보관, 변경 전후의 답과 점수·시간·비용을 비교, 좋아진 곳과 나빠진 곳을 읽고 다음 변경을 고름). 운영에서 발견한 요청을 다음 평가에 반영한다(보관한 평가 사례·변경 전후 비교 / 실제 사용의 새 요청·결과·의견: 새로운 사용 조건을 평가에 추가하고 다른 사례에서도 원하는 행동이 유지되는지 봄). 자동 점수를 읽을 때는 평가 기준과 근거도 본다(기록: 어떤 입력과 처리가 있었고 무슨 답이 나왔는가 / 평가: 어떤 기준으로 그 답을 좋다고 보았는가). “평가자·기준·근거가 달라지면 같은 답의 점수도 달라질 수 있다.” LLMOps는 언어 모델을 쓰는 서비스를 평가하고 배포하며 개선하는 운영이다(지침·자료·모델·도구·코드의 변경을 관리하고, 실제 결과와 품질·시간·비용을 함께 읽으며, 필요한 기록을 연결해 다음 개선에 사용).

05기술 대안을 배우고 내 코드와 대조한다 · 개선 목적에 따라 바꿀 곳이 다르다p.104–105

자료 p.104–105

AI에게 기술 대안을 배우고 내 코드와 대조한다: “이 목적을 해결하는 기술적 방법들을 설명해줘. 현재 코드의 방식과 무엇이 다르고, 왜 달라지는지 알려줘.” “바로 바꿀 수 있는 부분과 구조를 바꿔야 하는 부분을 실제 파일과 공식 자료를 근거로 구분해줘.” 처음 보는 기술은 예와 동작 원리부터 배우고 이해한 대안을 비교한다. 개선 목적에 따라 바꿀 기술과 확인할 결과가 다르다(상태 안내를 개선한다면: 기다림·응답 시작을 구별, 서버 상태를 화면에 전달, 안내가 이해되는지 확인 / 응답 시간을 줄이려면: 느린 처리와 조건을 찾기, 관련 모델·입력·코드 변경, 시간과 답의 품질을 함께 비교). 선택 이유를 개요·변경 계획에 반영하고 바뀐 결과를 같은 목적에 비추어 읽는다.

같은 ‘대기 문제’라도 목적이 다르면 바꿀 곳이 다릅니다. 상태 안내를 개선하는 일은 화면·서버의 전달 경로를, 응답 시간을 줄이는 일은 모델·입력·코드를 바꾸며 확인할 결과도 달라집니다(안내가 이해되는가 / 시간과 품질을 함께). 요청문의 둘째 문장(“실제 파일과 공식 자료를 근거로 구분해줘”)은 AI의 설명을 근거와 대조하라는 7일차의 원칙(p.67–68, p.113)과 같습니다. 선택 이유를 7일차의 서비스 개요·결정 이유 문서에 반영하라는 마지막 단서도 7일차 p.34의 ‘선택한 기술뿐 아니라 선택한 이유도 기록한다’의 연장입니다.

이용자 자료는 어디로 전달되고 어디에 남는가(이용자 입력 → 서비스 처리 → 모델·외부 도구 / 자료 저장소·실행·평가 기록·화면·공유 결과: 실제 쓰는 경로를 따라 어떤 내용이 전달·저장·공개되는지 본다). 개인정보 처리는 수집부터 삭제까지 조건을 정한다(입력·수집: 목적에 필요한 정보와 처리 근거 / 외부 전송: 받는 서비스·전달 내용·이용 조건 / 저장·운영 기록: 남길 항목·접근자·보유 기간 / 공유·삭제: 공개 범위·지울 위치·요청 대응). 원자료를 쓸 권리와 생성 결과의 권리는 별개다(입력 자료·가져온 코드: 어떤 용도로 이용할 수 있나? 수정·공유·재배포 조건은? 출처와 이용허락을 읽는다 / 생성 결과: 타인의 표현을 침해하는가? 사람의 창작적 기여가 있는가? 이용과 권리 주장을 구별한다).

검증 · 개인정보의 수집·제공·파기·안전조치와 저작물의 정의 (조문) 조문 확인 슬라이드에 없는 보충

  • 개인정보 보호법 제15조(수집·이용): 개인정보처리자는 정보주체의 동의를 받은 경우 등 각 호의 어느 하나에 해당하면 개인정보를 수집할 수 있고 그 수집 목적의 범위에서 이용할 수 있습니다. 제17조(제공): 정보주체의 동의를 받은 경우 등에 개인정보를 제3자에게 제공(공유 포함)할 수 있고, 동의를 받을 때는 받는 자·이용 목적·항목·보유 및 이용 기간 등을 알려야 합니다. 슬라이드의 ‘외부 전송: 받는 서비스·전달 내용·이용 조건’(모델 제공사로 이용자 입력을 보내는 경우 등)이 이 조항들과 맞닿습니다.
  • 제21조(파기): 보유기간의 경과, 처리 목적 달성 등으로 불필요하게 되면 지체 없이 파기해야 하며(다른 법령에 따라 보존해야 하는 경우 제외), 파기할 때는 복구 또는 재생되지 않도록 조치해야 합니다. 슬라이드의 ‘지울 위치’가 중요한 이유는 실행·평가 기록(앞 절의 Langfuse 같은 추적 기록)에도 입력이 남을 수 있기 때문입니다(작성자 해석).
  • 제29조(안전조치의무): 개인정보가 유출되지 않도록 내부 관리계획 수립, 접속기록 보관 등 대통령령으로 정하는 바에 따라 기술적·관리적·물리적 조치를 해야 합니다. 이 조문은 2026-09-11 시행판에서 문구가 바뀌었습니다(이전 판: “분실·도난·유출·위조·변조 또는 훼손되지 아니하도록”, 현재 판: “유출등이 되지 아니하도록”). 오래된 자료의 인용 문구와 다를 수 있습니다.
  • 저작권법 제2조 제1호(현재 시행판): “저작물”은 인간의 사상 또는 감정을 표현한 창작물을 말합니다. 슬라이드의 ‘생성 결과: 사람의 창작적 기여가 있는가’는 이 정의의 ‘인간’이 요소라는 점과 연결되며, AI 생성물이 저작물인지의 판단은 사안별이라 이 정의만으로 결론을 내릴 수 없습니다(작성자 해석).

개인정보 보호법 제15·17·21조는 확인한 네 개 판에서 같았고, 제29조만 최근 개정되었습니다. 저작권법 제2조는 최근 개정된 판이 있어 현재 시행판(2026-10-29 시행)의 문구를 읽었습니다.

AI 기본법 적용은 역할과 제공 기능에 따라 달라진다(AI 결과물을 이용: AI로 만든 내용이나 코드를 자기 작업에 사용 / AI 기능을 서비스로 제공: 이용자가 AI 기능을 쓰도록 제품·서비스를 제공. 사업 해당 여부와 실제 제공 기능을 확인한 뒤 적용 의무를 판단한다). 서비스 이용 전 고지(해당 서비스가 AI에 기반해 운용된다는 사실을 알림)와 생성 결과 표시(이 결과가 생성형 AI로 만들어졌다는 사실을 알림)는 다르다(AI사업자에게 적용되는 조건을 먼저 확인 · 외부 공유 결과의 표시도 별도 검토). 고영향 여부는 사용 영역과 실제 영향을 함께 본다(고영향 AI는 법이 정한 영역에서 생명·안전·기본권에 중대한 영향이나 위험을 줄 수 있는 AI다: 누구에게 어떤 판단을 제공하는지 확인, 결과가 권리·기회에 어떤 영향을 주는지 살핌, 현재 기능에 해당하는 공식 기준을 적용).

검증 · AI 기본법의 고지·표시·고영향 조항 (조문과 판 이력) p.109–111 정확히 일치

  • 제31조(투명성 확보 의무): ① 인공지능사업자는 고영향 인공지능이나 생성형 인공지능을 이용한 제품·서비스를 제공하려는 경우 해당 인공지능에 기반하여 운용된다는 사실을 이용자에게 사전에 고지해야 합니다(슬라이드의 ‘서비스 이용 전 고지’). ② 생성형 인공지능을 제공하는 경우 그 결과물이 생성형 인공지능에 의하여 생성되었다는 사실을 표시해야 합니다(‘생성 결과 표시’). ③ 실제와 구분하기 어려운 가상의 음향·이미지·영상 등은 이용자가 명확하게 인식할 수 있는 방식으로 고지 또는 표시해야 합니다. 의무의 주체는 ‘인공지능사업자’이므로 슬라이드의 “AI사업자에게 적용되는 조건을 먼저 확인”이 맞고, 5일차 p.92에서 확인한 같은 조항입니다.
  • 제2조 제4호(고영향 인공지능): “사람의 생명, 신체의 안전 및 기본권에 중대한 영향을 미치거나 위험을 초래할 우려가 있는 인공지능시스템으로서” 법이 나열한 영역(에너지 공급, 먹는물 생산, 보건의료, 의료기기, 원자력시설, 범죄 수사나 체포를 위한 생체인식정보의 분석·활용, 채용·대출 심사 등 개인의 권리·의무에 중대한 영향을 미치는 판단, 교통수단·교통체계, 공공서비스의 자격 확인·결정, 학생 평가, 그 밖에 대통령령으로 정하는 영역)에서 활용되는 것입니다. 슬라이드의 “법이 정한 영역에서 생명·안전·기본권에 중대한 영향이나 위험”과 같습니다.
  • 제33조(고영향 인공지능의 확인): 인공지능사업자는 자신이 제공하는 인공지능이 고영향에 해당하는지 사전에 검토해야 하며, 필요하면 과학기술정보통신부장관에게 해당 여부의 확인을 요청할 수 있습니다. 제34조: 고영향 인공지능을 제공하는 사업자는 위험관리방안의 수립·운영, 설명 방안, 이용자 보호 방안, 사람의 관리·감독, 조치 내용을 확인할 수 있는 문서의 작성·보관 등을 이행해야 합니다.

제31·33·34조는 2026-01-22 시행판부터 2027-04-21 시행 예정판까지 네 개 판에서 문구가 모두 같음을 이력으로 확인했습니다. 슬라이드가 말하는 “사업 해당 여부와 실제 제공 기능을 확인한 뒤 적용 의무를 판단한다”와 “현재 기능에 해당하는 공식 기준을 적용한다”는 제33조의 사전 검토 의무가 구체적 근거입니다. 이 서비스가 채용·대출 심사·학생 평가 같은 영역에 쓰이면 고영향 여부를 먼저 검토해야 합니다.

자료 p.112 · 공개 범위

기능·자료·운영 조건에 맞춰 공개 범위를 정한다(누가 어떤 기능을 사용할지 정하면 필요한 자료·권한·안내도 구체화된다). 자료를 전달하고 보관할 범위를 정한다. 이용 조건과 안내·표시를 실제 화면에 반영한다. 접속·핵심 기능·기록·중단 방법을 함께 확인한다.

공개 범위를 정하면 앞의 조문이 구체적으로 연결됩니다. 누가 쓰는지(대상) → 어떤 자료가 오가는지(개인정보 제15·17조) → 얼마나 보관하고 언제 지우는지(제21조) → 어떤 안내·표시가 필요한지(AI 기본법 제31조) → 고영향 영역인지(제33조) 순으로 확인합니다. 4일차 오후 둘째의 개인정보·이용허락 확인과 같은 절차입니다.

08핵심 정리

  • 기능을 더하기 전에 무엇이 문제인지를 사용자에게서 찾고, 어려움(모름·느림·도움이 안 됨)에 따라 바꿀 곳이 다릅니다. 다른 제품의 리뷰와 AI의 추측은 내 사용자의 반응이 아닙니다.
  • 실행 기록에서 전체 시간에는 하위 시간이 포함되므로 더하지 않습니다(3.1초 + 0.4 + 2.6 = 6.1초는 두 번 센 값). 답이 달라졌다면 바꾼 입력·조건도 함께 읽습니다(8일차: 자료 하나와 순서가 동시에 바뀜).
  • 품질·대기 시간·비용은 서로 다른 결과이고, 실험 추적은 변경 조건과 결과를 함께 보관하며, 자동 점수는 평가 기준과 근거까지 읽습니다.
  • 개인정보는 수집·이용(제15조)·제공(제17조)·파기(제21조)·안전조치(제29조, 문구 개정)로, 저작물은 ‘인간의 사상 또는 감정을 표현한 창작물’이라는 정의에서 출발합니다.
  • AI 기본법 제31조는 인공지능사업자에게 사전 고지와 생성 결과 표시를 요구하고, 고영향 인공지능은 정해진 영역(채용·대출 심사·학생 평가 등)에서 사전 검토(제33조)와 안전·신뢰 조치(제34조)가 따릅니다.
