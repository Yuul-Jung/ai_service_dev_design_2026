npm init → npm install is-odd@3.0.1 을 실행한 뒤 package.json dependencies: {"is-odd": "^3.0.1"} ← 사용하는 패키지와 허용 범위(^), scripts에 실행 명령 package-lock.json is-odd = 3.0.1 · 함께 잠긴 하위 패키지: is-number ← 설치된 구체적인 버전 생성된 것: node_modules · package-lock.json · package.json

슬라이드의 “package.json은 사용하는 패키지와 실행 명령을 적고, package-lock.json은 설치할 패키지들의 구체적인 버전을 기록한다”가 확인됩니다. ^3.0.1은 ‘3.0.1 이상의 호환 범위’이고 잠금 파일은 실제로 설치된 정확한 버전(3.0.1)과 내가 직접 고르지 않은 하위 패키지까지 기록합니다. 그리고 설치(npm install)가 끝나도 서비스가 켜진 것은 아닙니다(p.55). 설치는 부품 준비, 개발 서버 실행은 동작시키는 일입니다.

검증 · 로컬 주소와 포트 (실제 실행) p.57·p.60 확인

http://localhost:3000 = localhost(접속하는 기기 자신) + 3000(그 기기의 서비스에 접근할 포트) 서버 한 개를 3000 포트에 켜고 접속 → 응답 코드 200 같은 3000 포트에 서버를 하나 더 켜려 하면 → OSError: [Errno 98] Address already in use

Next.js 공식 문서도 개발 서버를 켠 뒤 http://localhost:3000에 접속하라고 안내합니다(기본 포트). 포트는 한 번에 한 서비스만 쓸 수 있어서, 이미 켜진 서버가 있으면 두 번째 서버가 시작에 실패하고 그 오류는 서버를 실행한 터미널에 나타납니다(p.60). 슬라이드의 “다른 사람의 컴퓨터에서 같은 주소를 열어도 내 서비스가 아니다”는 localhost가 ‘접속하는 기기 자신’이라는 뜻의 직접적인 결과입니다.

검증 · 환경 변수와 비밀키의 위치 (Next.js 공식 문서) p.58 확인

Next.js 공식 문서는 이름 앞에 NEXT_PUBLIC_이 붙지 않은 환경 변수는 Node.js 환경에서만 쓸 수 있고 브라우저에서는 접근할 수 없으며, 접두사를 붙이면 값이 빌드할 때 브라우저로 전달되는 JavaScript 번들에 그대로 박힌다(inline)고 설명합니다. 그래서 슬라이드의 “.env 파일에 적었다고 모두 비밀이 되는 것은 아니다, 브라우저에 전달된 값은 사용자가 볼 수 있다, 모델 API 비밀키는 서버 쪽 설정으로 관리한다”가 정확합니다. 변수 이름만 보고도 어느 쪽에 노출되는지 달라지므로, 비밀키에 ‘공개’ 접두사를 붙이면 안 됩니다.

03변경이 파일에서 실행으로 · 동작하는 것과 목적에 맞는 것p.61–68

이번 작업: 사진 입력은 유지하고 추가 정보 입력란을 만든다. 프로젝트 폴더의 index.html에 재료와 조리 조건을 적는 입력란(이름: details)을 추가한다. 변경 전: 사진은 받을 수 있지만 추가 정보를 적을 곳은 없다. 변경 후: “파일에 추가한 입력란이 실행 화면에 나타났다.” 파일이 만들어진 것과 실행되는 것은 다르며, 변경된 파일이 현재 실행에도 반영됐는지 확인한다(p.53).

Claude Code의 중단 키(Ctrl+C)는 공식 사용 안내에 접속할 수 없어 확인하지 못했습니다. 공식 변경 기록에는 Ctrl+C의 동작이 상황별로(입력을 지울 때, 대화 상자에서 두 번 누를 때 등) 나뉘어 있음을 보여 주는 항목이 있어 키의 동작은 상황과 버전에 따라 다를 수 있습니다. 이 쪽의 핵심 주장인 “중단은 되돌리기가 아니다, 이미 수정한 파일이 남는다”는 도구와 무관한 일반 원리이며, Git 비교(p.77)로 바뀐 파일부터 확인한다는 순서와 이어집니다.

실행됐다프로그램을 열 수 있다

세 줄은 위로 갈수록 쉬운 확인이고 아래로 갈수록 사용자 관점의 확인입니다. 오전에 정한 완료 기준(입력·결과·예외)이 세 번째 줄의 비교 대상입니다. 질문 5(p.66)는 “앞서 지시한 목적에 맞게 구현되었는지 실제 결과를 검토하고, 보완할 부분을 파악해줘”이며 “문제를 수정한 뒤 해당 기능과 연결된 부분을 다시 확인해줘”로 이어집니다.

계획대로 만들었어도 목적을 놓칠 수 있으므로 계획과 실제 구현을 비교하고, 그 계획도 원래 목적에 맞는지 다시 읽습니다(p.67). 다른 AI의 검토(p.68)도 원래 목적·현재 계획·실제 파일과 실행 결과에서 시작해야 하고, 그 의견을 원래 작업 AI에게 전달해 “이 지적의 근거를 실제 파일과 대조해줘”라고 요청합니다. 다른 AI의 검토 역시 근거를 확인할 의견입니다.

터미널에서는 입력한 명령 아래에 실행 결과가 표시된다(명령과 결과를 구별해 읽는다). 변경 비교에서는 파일 목록에서 대상을 고르고 추가·삭제된 부분을 읽는다. AI에게는 “마지막 커밋 이후로 무엇이 바뀌었는지 정리해줘”라고 요청하고, 변경된 파일과 실제 결과를 함께 보며 요청한 범위를 벗어난 변경은 없는지 확인한다.

p.78의 요청은 AI의 설명을 변경 비교와 대조하라는 뜻입니다. AI의 요약만 믿지 말고 변경 비교 화면에서 실제로 바뀐 줄을 보면, 요청하지 않은 파일이 수정된 경우를 찾을 수 있습니다.

07핵심 정리

  • 구현 전에 계획과 AI가 스스로 판단한 부분을 읽고, 계획 모드(조사·계획)와 실행 권한(허용 범위)은 따로 확인합니다.
  • 설치는 부품 준비, 실행은 동작이며, package.json은 패키지·명령, package-lock.json은 정확한 버전입니다. localhost:3000은 내 기기의 3000번 포트이고 포트는 한 서비스만 씁니다.
  • 공개 접두사가 붙은 환경 변수는 브라우저로 전달되므로 모델 API 비밀키는 서버 쪽에 둡니다.
  • 실행됨 → 동작함 → 목적에 맞음은 서로 다른 확인이며, 다른 AI의 검토도 근거를 확인할 의견입니다.
  • 지침 파일(AGENTS.md·CLAUDE.md)은 있다고 반영되는 것이 아니고, 저장·커밋·푸시는 서로 다른 상태이며 코드를 되돌려도 외부 데이터는 그대로입니다.
